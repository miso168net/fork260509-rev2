# Feature Specification: getUserRoutes 改讀 sys_menu(單一真相源)

**Feature Branch**: `018-userroutes-sys-menu`

**Created**: 2026-05-31

**Status**: Draft

**Input**: Phase 0 brainstorm: [`docs/superpowers/018-userroutes-sys-menu.md`](../../docs/superpowers/018-userroutes-sys-menu.md)

> 把登入使用者的動態導覽選單樹,從一份「寫死的 in-code 定義」改成由**中央選單資料表**(單一真相源)供應;並修正選單資料表中「使用者明細」項缺漏的欄位,使其對齊前端權威定義。角色可見性過濾與對外 wire 形狀**維持不變**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 導覽選單由中央選單資料表供應、角色可見性不變 (Priority: P1)

登入的後台使用者驗證通過後,會拿到「依其角色過濾後」的導覽選單樹。本 feature 之後,這份選單樹改由**中央選單資料表**供應,而非另一份寫死的清單。各角色**看到哪些項目、順序、巢狀結構完全不變**——改的只是資料來源。

**Why this priority**: 這是本 feature 的核心價值——消除「選單顯示來源」與「選單資料來源」雙源並存的漂移風險。雙源並存時,兩邊可能悄悄不一致(本 feature 起因正是發現了一處這種不一致)。統一為單一真相源後,選單資料表成為唯一權威,未來對選單資料的變更才有單一施力點。

**Independent Test**: 以三個 seed 角色(超級管理員 / admin / 一般使用者)分別登入取路由,確認可見的選單樹與改動前**逐項相同**(項目、順序、巢狀、父層在子項全不可見時整個隱藏的行為),且來源確為選單資料表。

**Acceptance Scenarios**:

1. **Given** 一個登入的超級管理員,**When** 取得其路由,**Then** 看到 `home` + 完整 manage 區(使用者 / 角色 / 選單 / 使用者明細),與改動前完全一致。
2. **Given** 一個登入的 admin,**When** 取得其路由,**Then** 看到 `home` + manage 區但只含被授權的子項(使用者、使用者明細),與改動前完全一致。
3. **Given** 一個登入的一般使用者,**When** 取得其路由,**Then** 只看到 `home`(manage 區因無任一可見子項而整個隱藏),與改動前完全一致。
4. **Given** 選單來源,**When** 產生路由樹,**Then** 該樹衍生自中央選單資料表,而非任何寫死的清單。

---

### User Story 2 - 修正「使用者明細」項的資料缺漏(對齊前端權威) (Priority: P2)

選單資料表中「使用者明細」這一項先前資料不完整:缺了它的**檢視畫面參照**與**把路由 id 傳入頁面的旗標**。這個缺漏在「選單由寫死清單供應」時被遮住,一旦改由資料表供應就會浮現,導致使用者明細頁拿不到 id。本 story 把該筆資料修正成對齊前端權威定義。

**Why this priority**: 正確性前置條件——不修這筆資料,US1 把來源換成資料表時就會回歸(使用者明細頁壞掉)。它是一個被雙源遮住的潛在資料保真 bug。

**Independent Test**: 檢視被授權角色取得的路由中「使用者明細」項,確認它帶有檢視畫面參照與 id 傳入旗標,與前端權威定義相符。

**Acceptance Scenarios**:

1. **Given** 選單資料表,**When**「使用者明細」項被供應給被授權角色,**Then** 它包含其檢視畫面參照與「id 傳入頁面」旗標。
2. **Given** 一個超級管理員 / admin,**When** 導覽至某使用者明細頁,**Then** 該頁正確接收到該筆紀錄的 id。

---

### Edge Cases

- **僅作版面的父層節點(無檢視畫面)**:manage 父層本身不對應任何檢視畫面(只是版面容器);它在路由樹中仍須正確輸出、不因「無檢視畫面」而出錯。
- **未設順序的節點**:某節點未設定排序值時,須有穩定且一致的排序結果(排在有序兄弟節點之後),與改動前順序一致。
- **角色在某父層下無任何可見子項**:父層須整個隱藏(沿用既有的「父層依子項衍生可見性」剪枝行為)。
- **選單資料表與前端權威對某節點欄位不一致**:以前端權威為準(資料被修正成與前端一致)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 回傳給登入使用者的動態路由樹 MUST 衍生自中央選單資料表(權威選單紀錄),而非另一份寫死的定義。
- **FR-002**: 路由樹的角色可見性過濾 MUST 維持不變——每個角色看到的選單項目、順序、巢狀、父層剪枝行為,與改動前**逐項相同**。
- **FR-003**: 回傳的路由樹 MUST 保留既有 wire 形狀與所有選單節點的欄位值(識別碼、名稱、路徑、檢視畫面參照、標題、i18n 鍵、圖示、順序、巢狀、各顯示旗標),使前端渲染結果一致。
- **FR-004**:「使用者明細」選單項 MUST 帶有其檢視畫面參照與「把路由 id 傳入頁面」旗標,對齊前端權威路由定義。
- **FR-005**: 中央選單資料表 MUST 被修正,使「使用者明細」紀錄持有上述檢視畫面參照與 id 傳入旗標(此前不完整),且此修正為**前向**(forward-only)、不回改既有已套用的資料定義。
- **FR-006**: 登入前的公開 constant 路由(錯誤頁、登入頁、iframe 承載頁)MUST 維持不變、且持續獨立於選單資料表(不在其中)。
- **FR-007**:「某具名路由對此使用者是否可見」的查詢 MUST 維持不變。
- **FR-008**: 本 feature MUST 對業務紀錄為唯讀(不新增任何使用者層級的建立 / 修改 / 刪除、不記 operator);唯一的資料變更是對 seed 選單紀錄的系統級修正(與「審計欄 / operator 歸屬」已擱置的決定一致)。

### Key Entities *(include if feature involves data)*

- **選單紀錄(sys_menu)**:一個可導覽選單項的權威定義——識別(路由名稱)、顯示(標題、圖示、i18n 鍵)、配置(路徑、父層、順序)、行為旗標(keep-alive、隱藏於選單、constant、active-menu)、檢視畫面參照,以及額外路由屬性(含「id 傳入頁面」旗標)。本 feature 起後,它是動態導覽選單的**單一真相源**。
- **角色↔選單可見性政策**(既有授權政策):決定某角色可看到哪些選單項。本 feature **重用、不變**。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對三個 seed 角色,本 feature 後回傳的導覽選單與改動前**逐項相同**(項目、順序、巢狀)——零可觀察回歸。
- **SC-002**: 回傳給被授權角色的「使用者明細」項帶有其檢視畫面參照與 id 傳入旗標(此前缺漏),且導覽至使用者明細頁時 100% 正確接收紀錄 id。
- **SC-003**: 導覽選單自此只有單一權威來源;不再存在第二份可能漂移的寫死選單定義。
- **SC-004**: 登入前 constant 路由與「路由是否可見」查詢不受影響(驗證維持不變)。

## Assumptions

- 中央選單資料表(sys_menu)**已存在**且已 seed 6 個業務選單節點(由前序 017 落地)。
- 「正確欄位值」的權威來源 = 前端路由定義(base-web),依專案原則 §I.1 / §I.3。
- 角色↔選單可見性政策(既有授權引擎)已治理各角色可見項,本 feature 直接重用、不改。
- 本 feature 對業務紀錄唯讀;唯一資料變更是對一筆 seed 選單紀錄的系統級修正,不涉 operator 歸屬(審計欄工作已擱置至 Phase 4 A)。
- **Out of scope**:選單的建立 / 修改 / 刪除(menu CRUD)、把選單資料表以外的其他消費者也改讀此表、login 前 constant 路由的改造、「id 傳入旗標」以外的額外路由屬性 route 化。
