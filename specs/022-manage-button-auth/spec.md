## Clarifications

### Session 2026-06-03 (Phase 0 brainstorm 親決 K1–K4 + C1–C3)

- Q: 「按鈕權限」要管理的按鈕來源? → A: **per-menu 真實按鈕(K1)**。每個選單定義其自身按鈕(碼 + 描述),可用按鈕清單 = 全選單按鈕之聚合;不採「抽象 demo 碼」或新增獨立按鈕資料表。
- Q: 指派後在哪看到效果 / 範圍含不含改業務頁? → A: **單一業務頁 pilot = 用戶管理頁(K2)**。本波把用戶管理頁的操作按鈕接上按鈕權限把關(端到端真有效果);角色管理頁、選單管理頁的按鈕 gating 留後續 feature。
- Q: 現行 demo 按鈕碼(B_CODE1/2/3)怎麼處理? → A: **保留(K3)**。既有「角色→按鈕」分布逐字保留為回歸基線,真實按鈕為額外新增。
- Q: 既有 demo 頁(toggle-auth,目前已不可達)怎麼辦? → A: **救活(K4)**。把該 demo 選單納入選單定義 + 給予可見性把關,使其重新可達、其按鈕依授權顯示。**已知代價**:導覽輸出(getUserRoutes)因新增該 demo 選單而需重訂逐字基線(re-base)。
- Q: 編輯介面以什麼為勾選鍵? → A: **按鈕碼(C1)**。按鈕無天然數值 id,可見性把關以按鈕碼為穩定鍵,介面以碼勾選。
- Q: demo 選單給哪些角色可達? → A: **三角色皆可達(C2)**,各自看到自己被授予的按鈕。
- Q: pilot 按鈕與指派對象? → A: **用戶管理頁的新增/編輯/刪除(C3)**,指派分布讓三角色有可見差異(最高權限全給、其餘部分給)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 維運者編輯角色的可用按鈕,業務頁即時生效 (Priority: P1)

身為系統維運者(最高權限),我希望在「角色管理」頁為某角色設定其可用的按鈕集合(於按鈕清單勾選),讓該角色的人員登入後,在業務頁(本波 pilot = 用戶管理頁)只看到被授權的操作按鈕(如新增 / 編輯 / 刪除);變更**即時反映**、無需重啟,且跨服務實例一致。

**Why this priority**: 這是「按鈕權限」從「建置期硬編」變成「**維運期可編輯**」並且**真正在畫面生效**的關鍵一步 —— 它補上 grounding 揭露的「指派了按鈕卻無消費者」缺口(現況業務頁完全不檢查按鈕權限)。可單獨交付(指派/移除按鈕 → 用戶管理頁對應操作鈕出現/消失)即構成價值。

**Independent Test**: 以最高權限身分為某角色勾選一組按鈕並儲存 → 以該角色人員身分登入用戶管理頁,被授予的操作鈕顯示、未授予的不顯示;移除某按鈕後重登 → 對應操作鈕消失;期間其他角色不受影響。

**Acceptance Scenarios**:

1. **Given** 一個既有角色與一組已定義的按鈕, **When** 維運者勾選按鈕集並儲存, **Then** 該角色的按鈕授權更新(硬替換),該角色人員於用戶管理頁即時(無需重啟)看到被授予的操作按鈕。
2. **Given** 某角色已被授予某按鈕, **When** 維運者取消勾選該按鈕並儲存, **Then** 該角色人員於用戶管理頁不再看到對應操作按鈕,其餘授權維持不變。
3. **Given** 編輯介面開啟某角色, **When** 載入, **Then** 該角色目前被授予的按鈕以勾選狀態正確預載(以按鈕碼為鍵對映正確)。

---

### User Story 2 - 可用按鈕來源為選單所定義的真實按鈕 (Priority: P2)

身為系統維運者,我希望可用按鈕清單來自各選單自身定義的真實按鈕(碼 + 描述)之聚合,讓「指派給角色的按鈕」對應到真實的選單操作,而非抽象佔位碼。

**Why this priority**: 「按鈕來源」決定整個按鈕權限模型是否名副其實;但它服務於 US1 的指派與生效,故次要。可單獨驗證(在某選單定義一個按鈕 → 它出現在可指派清單)。

**Independent Test**: 於選單定義新增一個按鈕(碼 + 描述)→ 該按鈕出現在角色編輯介面的可指派清單;聚合涵蓋所有有效選單的按鈕;已軟刪選單的按鈕不出現。

**Acceptance Scenarios**:

1. **Given** 數個選單各自定義了按鈕, **When** 維運者開啟某角色的按鈕編輯介面, **Then** 可指派清單為所有有效選單按鈕之聚合(去重、以碼識別)。
2. **Given** 一個已軟刪的選單, **When** 開啟按鈕編輯介面, **Then** 該選單的按鈕不出現於可指派清單。

---

### User Story 3 - 既有按鈕權限零退化 + demo 頁救活 (Priority: P3)

身為系統維運者,我希望把硬編按鈕權限改為可編輯來源後,既有的「角色→按鈕」分布**逐字保留**(登入資訊回報的按鈕集不變),且既有示範頁(toggle-auth)重新可達、其按鈕依授權正確顯示。

**Why this priority**: 保障「行為零退化」與既有 demo 的可驗證性;屬安全網與佐證,優先序最低但必要。

**Independent Test**: 未對任何角色編輯按鈕前 → 三角色登入資訊回報的按鈕集與本波前逐字一致;以三角色分別登入 demo 頁 → 各見自己被授予的按鈕。

**Acceptance Scenarios**:

1. **Given** 尚未編輯任何角色按鈕, **When** 任一既有角色取得登入資訊, **Then** 其按鈕集與本波前逐字一致(既有分布保留)。
2. **Given** demo 選單已納入選單定義並給予可見性, **When** 三角色分別登入並導覽至 demo 頁, **Then** demo 頁可達,且各角色僅見自己被授予的按鈕。

### Edge Cases

- **未編輯回歸(雙基線)**:未編輯任何角色按鈕時,登入資訊回報的按鈕集 MUST 與本波前逐字一致;導覽因 demo 選單救活而**重訂逐字基線**(含 demo 選單),此為本波 intended 變更、非退化。
- **硬替換語意**:儲存某角色可用按鈕集 = 取代其舊集(非增量);本波不提供復原。
- **即時 + 跨實例**:按鈕授權變更後不重啟即反映;多服務實例時所有實例即時一致。
- **非法輸入**:指派不存在的按鈕碼 / 角色不存在 / 非法角色識別碼 → 業務錯誤(非授權/基建類)。
- **自鎖**:按鈕權限非導覽存取(移除按鈕只影響業務頁操作鈕之顯隱,不影響頁面可達性),**無自鎖風險**;本波 pilot 不對「角色管理頁的按鈕授權觸發鈕」做 gating。
- **pilot 邊界**:僅用戶管理頁的操作鈕受按鈕權限把關;角色 / 選單管理頁的操作鈕本波維持一律顯示。
- **多角色聯集**:多角色使用者的可用按鈕為各有效角色授權之去重聯集(順序穩定)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供「角色 × 按鈕權限」編輯能力:維運者可設定某角色可用的按鈕集合(硬替換),寫入既有權限把關;變更 MUST **即時反映**(無需重啟)且 MUST 在所有服務實例即時一致生效。
- **FR-002**: 系統 MUST 提供讀取某角色目前可用按鈕集的能力(供編輯介面預載勾選狀態)。
- **FR-003**: 可用按鈕清單 MUST 為各選單所定義之按鈕(碼 + 描述)之聚合(去重);編輯介面以**按鈕碼**為穩定鍵操作;**已軟刪選單的按鈕 MUST NOT** 出現於可指派清單。
- **FR-004**: 系統 MUST 使至少一個業務頁(本波 pilot = **用戶管理頁**)的操作按鈕(新增 / 編輯 / 刪除)依使用者被授予的按鈕權限顯示或隱藏;角色管理頁、選單管理頁的按鈕 gating MUST NOT 在本波。
- **FR-005**: 系統 MUST 救活既有示範頁(toggle-auth):將其選單納入選單定義並給予可見性把關,使其重新可達;其按鈕 MUST 依使用者授權顯示;三角色 MUST 各可達並見各自被授予的按鈕。
- **FR-006**: 將硬編按鈕權限改為可編輯來源後,既有「角色→按鈕」分布(登入資訊回報的按鈕集)MUST **逐字保留**(回歸);新定義的真實按鈕為額外授予,不影響既有碼之輸出。
- **FR-007**: 按鈕權限編輯 MUST 限最高權限管理員(Super)存取;其他已認證使用者 MUST 被拒(權限不足),未認證請求 MUST 被拒(沿既有授權把關與錯誤碼)。
- **FR-008**: 業務驗證錯誤(非法按鈕碼 / 角色不存在 / 非法識別碼)MUST 以既有「業務錯誤」碼回應(非授權/基建類);回傳沿既有統一回應格式與對外字串識別碼契約。
- **FR-009**: 本波 MUST NOT 包含:用戶管理頁以外業務頁的按鈕 gating、按鈕權限的復原(restore)/ 版本管理 / 保護標記、按鈕定義的完整 UI 管理流程(超出救活 demo + pilot 所需),皆留後續 feature。
- **FR-010**: 既有能力 MUST NOT 因本波而被破壞(回歸),**唯一 intended 例外**為:導覽逐字基線因 demo 選單救活而重訂(含 demo 選單)。其餘 —— 選單可見性編輯(前波)、選單三讀端 / 寫端、角色 / 用戶讀寫端、既有授權把關(login/enforce 階梯)、per-role home —— MUST 維持原行為。
- **FR-011**: 按鈕權限變更 MUST 記錄稽核中介資料(操作者 + 變更前後集)。

### Key Entities *(include if feature involves data)*

- **按鈕權限(Button permission)**:角色 × 按鈕的授權(由既有權限把關機制提供、按鈕以碼為鍵)。本波新增**維運期編輯路徑**(設定 / 讀取某角色可用按鈕集)並把登入資訊的按鈕來源從建置期硬編改為此可編輯來源;**不新增資料表、不改授權機制本身**;變更為硬替換、即時生效、跨實例一致。
- **選單按鈕(Menu button)**:選單定義內所含的按鈕(碼 + 描述)。本波 seed 真實按鈕(用戶管理頁所需 + demo 頁原有碼),並以全選單按鈕之聚合作為可用按鈕清單;承既有選單資料表的按鈕屬性,不新增資料表。
- **示範選單(Demo menu / toggle-auth)**:既有但目前不可達的示範頁。本波將其納入選單定義 + 可見性把關使其可達,作為按鈕授權的端到端佐證之一。
- **業務頁操作按鈕(pilot 消費者)**:用戶管理頁的新增 / 編輯 / 刪除操作鈕;本波接上按鈕權限把關使其依授權顯隱。

## Success Criteria *(mandatory)*

> 下列百分比指對所列舉的代表性 case 矩陣**全數通過**(各類正反例至少各一),非統計抽樣。

### Measurable Outcomes

- **SC-001**: 維運者可於角色管理頁完整設定某角色可用按鈕,變更 100% **即時反映**(指派的出現、移除的消失)於該角色於用戶管理頁所見操作鈕,**無需重啟**。
- **SC-002**: 按鈕權限變更在**所有服務實例 100% 即時一致**生效(不因實例不同而看到舊授權)。
- **SC-003**: 可用按鈕清單 100% 為有效選單按鈕之聚合(去重);已軟刪選單按鈕 0% 出現。
- **SC-004**: pilot 生效:用戶管理頁的新增 / 編輯 / 刪除鈕 100% 依使用者被授予按鈕顯隱(授予者見、未授予者不見)。
- **SC-005**: demo 救活:三角色 100% 可達 demo 頁,且各角色於該頁所見按鈕 100% 等於其被授予集。
- **SC-006**: 回歸 —— 未編輯任何角色按鈕時,三角色登入資訊回報的按鈕集 100% 與本波前逐字一致;導覽逐字輸出 100% 等於本波重訂之新基線(含 demo 選單);選單 / 角色 / 用戶讀寫端、既有授權階梯、per-role home 100% 維持原行為。
- **SC-007**: 編輯授權正確:最高權限者(Super)成功率 100%,其他已認證使用者與未認證請求被拒比例 100%(0% 越權編輯);變更 100% 記錄稽核(操作者 + 變更前後集)。

## Assumptions

- **沿用既有權限把關機制**:按鈕權限走既有權限把關(既有 Casbin policy,以按鈕碼為鍵);本波只加**維運期編輯路徑**並把登入資訊按鈕來源改讀此把關,不改授權機制、不新增資料表。
- **變更即時生效 + 跨實例一致**:沿既有「一致性優先」基建(既有訊息發布/訂閱機制)使按鈕授權變更在所有實例即時生效;單一實例下亦即時。
- **硬替換、不可復原**:設定某角色可用按鈕集為取代其舊集;復原 / 保護標記 / 版本管理留後續 feature。
- **按鈕以碼為穩定鍵**:按鈕無天然數值 id,可見性把關與編輯介面均以按鈕碼為鍵(對齊既有把關以碼為鍵的事實)。
- **無自鎖防護需求**:按鈕權限非導覽存取(僅影響業務頁操作鈕顯隱),移除不致使維運者失去頁面可達性 → 不需自鎖 guard(對照前波選單可見性需自鎖防護)。
- **沿用既有資料表**:選單資料表(承其按鈕屬性 + 新增 demo 選單列 + seed 真實按鈕)、角色按鈕授權走既有把關、既有稽核機制;按鈕識別以碼。
- **前端沿用既有角色管理頁的按鈕授權對話框**(button-auth-modal,目前為未接線 placeholder),本波接上既有受管接線軌道,並將其勾選鍵由佔位 id 改為按鈕碼。
- **demo 救活的導覽基線代價**:救活 demo 選單會使導覽逐字基線重訂(含 demo 選單),此為本波 intended 變更;per-role home 與既有業務選單可見性不受影響。
- **wire 形狀與前端送出形**細節於規劃 / 研究階段以實際 code 與既有契約對齊(plan/research);本波不在 spec 固定 endpoint / handler 命名。
