## Clarifications

### Session 2026-06-02 (Phase 0 brainstorm 親決 M1–M5)

- Q: 本波範圍? → A: **MenuAuth = 角色×選單可見性編輯 + per-role home(M1)**。「角色×按鈕權限編輯」(ButtonAuth)機制不同(現由登入資訊的程式內對映供應、不走可見性把關引擎)→ 獨立後續 feature,不在本波。
- Q: 可見性變更如何生效、是否可復原? → A: **即時生效、硬替換、不可復原(M2)**。設定某角色可見選單集 = 取代其舊集;變更即時反映於授權與導覽,**不重啟**;本波不提供復原(restore)/版本管理/保護標記(那是後續「受管 policy 層」feature)。變更記稽核。
- Q: 多服務實例時可見性一致性? → A: **變更在所有實例即時一致生效(M3)**——沿既有「一致性優先」設計,不因實例不同而看到舊可見性。
- Q: 角色落地頁(home)要做嗎? → A: **要(M4)**。角色新增「落地頁」屬性;runtime 導覽回該角色 home;多角色使用者取第一個有效角色的 home;未設定者沿用系統預設首頁。未編輯任何角色時導覽輸出維持與本波前逐字一致。
- Q: 防自鎖? → A: **核心導覽可見性保護(M5)**。移除會造成維運者自身失去核心導覽(尤其選單管理頁本身)的可見性 → 被拒;批次清空亦受此保護(鏡像選單種子保護)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 維運者編輯角色的可見選單 (Priority: P1)

身為系統維運者(最高權限),我希望在「角色管理」頁為某角色設定其可見的選單集合(於選單樹勾選),讓該角色的人員登入後只看到被授權的選單;且因 runtime 導覽即時讀取可見性把關,變更**即時反映**於該角色的側欄導覽。

**Why this priority**: 這是「選單由權限把關決定可見」從「建置期硬編」變成「**維運期可編輯**」的關鍵一步,也直接補上選單寫端(前一波)留下的缺口 —— 新建的選單在被指派可見性前不顯於導覽,本能力讓維運者把新選單指派給角色、使其真正出現在導覽。可單獨交付(指派/移除選單即時反映於導覽)即構成價值。

**Independent Test**: 以最高權限身分,為某角色勾選一組選單並儲存 → 該角色人員的 runtime 導覽即時出現被指派的選單;取消勾選某選單 → 該選單即時從該角色導覽消失;期間其他角色的導覽不受影響。

**Acceptance Scenarios**:

1. **Given** 一個既有角色與一組有效選單, **When** 維運者勾選選單集並儲存, **Then** 該角色的可見性把關更新、該角色 runtime 導覽即時(無需重啟)出現被指派的選單。
2. **Given** 某角色已可見某選單, **When** 維運者取消勾選該選單並儲存, **Then** 該選單即時從該角色導覽消失,其餘可見選單維持不變。
3. **Given** 編輯介面開啟某角色, **When** 載入, **Then** 該角色目前可見的選單集以勾選狀態正確預載(識別碼對映正確)。
4. **Given** 已被軟刪的選單, **When** 編輯某角色可見性, **Then** 該選單不出現於可指派集、亦不出現於已指派集。

---

### User Story 2 - 維運者設定角色落地頁(home) (Priority: P2)

身為系統維運者,我希望為某角色設定登入後的落地頁(home),讓不同角色的人員登入後落在各自合適的頁面。

**Why this priority**: 「落地頁」是角色化體驗的一部分,但相對選單可見性次要;可單獨驗證(設定角色 home → 該角色導覽回該 home)。

**Independent Test**: 為某角色設定一個落地頁並儲存 → 該角色人員的 runtime 導覽回報該落地頁;多角色使用者取第一個有效角色的落地頁;未設定的角色沿用系統預設首頁。

**Acceptance Scenarios**:

1. **Given** 一個既有角色, **When** 維運者設定其落地頁並儲存, **Then** 該角色 runtime 導覽回報的落地頁即為所設值,且寫入更新稽核(操作者 + 時間,成對)。
2. **Given** 一個同時具多個有效角色的使用者, **When** 取得 runtime 導覽, **Then** 落地頁取其第一個有效角色(以角色識別碼順序)的設定值。
3. **Given** 未設定落地頁的角色, **When** 取得 runtime 導覽, **Then** 落地頁為系統預設首頁。

### Edge Cases

- **自鎖保護**:移除會造成維運者自身失去核心導覽(尤其「選單管理頁」本身)的可見性 → 被拒(業務錯誤);批次清空某角色全部可見性若命中核心導覽 → 整批拒。
- **未編輯回歸**:未對任何角色編輯可見性/落地頁時,各角色 runtime 導覽輸出與常數路由 MUST 與本波前逐字一致(延續既有逐字基線鐵律)。
- **即時 + 跨實例**:可見性變更後,不重啟即反映於導覽;多服務實例時所有實例即時看到新可見性(不因實例不同而看到舊集)。
- **非法輸入**:指派不存在/已軟刪選單、角色不存在、非法識別碼 → 業務錯誤(非授權/基建類)。
- **硬替換語意**:儲存某角色可見集 = 取代其舊集(非增量);本波不提供復原。
- **多角色落地頁**:取第一個有效角色;若該角色未設定則退回系統預設首頁。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供「角色 × 選單可見性」編輯能力:維運者可設定某角色可見的選單集合,寫入既有可見性授權把關;變更 MUST **即時反映**於該角色的 runtime 導覽(無需重啟),且 MUST 在所有服務實例即時一致生效。
- **FR-002**: 系統 MUST 提供讀取某角色目前可見選單集的能力(供編輯介面預載勾選狀態)。
- **FR-003**: 可見性編輯於介面以選單識別碼操作;系統 MUST 與既有可見性把關的穩定鍵(選單路由名)正確對映;**已軟刪選單 MUST NOT** 出現於可指派集或已指派集。
- **FR-004**: 系統 MUST 提供「角色落地頁(home)」設定與讀取:可設某角色登入後落地頁;runtime 導覽 MUST 回該角色 home;**多角色使用者取第一個有效角色(以角色識別碼順序)的 home**;未設定者沿用系統預設首頁。
- **FR-005**: 可見性與落地頁編輯 MUST 限最高權限管理員(Super)存取;其他已認證使用者 MUST 被拒(權限不足),未認證請求 MUST 被拒(沿既有授權把關與錯誤碼)。
- **FR-006**: 系統 MUST 防止自鎖:移除會造成維運者自身失去核心導覽(尤其「選單管理頁」本身)可見性的操作 MUST 被拒(業務錯誤);批次清空命中核心導覽者 MUST 整批拒、不做部分執行。
- **FR-007**: 可見性變更與落地頁變更 MUST 記錄稽核中介資料 —— 可見性變更記操作稽核(操作者 + 變更前後集);落地頁變更成對寫入更新稽核(操作者 + 時間,對齊 §I.6)。
- **FR-008**: 業務驗證錯誤(自鎖 / 非法識別碼 / 角色不存在 / 選單不存在)MUST 以既有「業務錯誤」碼回應(非授權/基建類);回傳沿既有統一回應格式與對外字串識別碼契約。
- **FR-009**: 本波 MUST NOT 包含:角色 × 按鈕權限編輯(ButtonAuth)、可見性的復原(restore 已移除的可見性)、可見性 policy 的保護標記/版本管理(完整「受管 policy 層」),皆留後續 feature。
- **FR-010**: 既有能力 MUST NOT 因本波落地而被破壞(回歸):未編輯任何角色時 runtime 導覽既有逐字輸出與常數路由維持原樣;選單三讀端(列表/樹/頁面選項)、選單寫端、既有授權把關(login/enforce 階梯)、既有 user/role 寫端與清單顯示皆維持原行為。

### Key Entities *(include if feature involves data)*

- **選單可見性授權(Menu visibility)**:既有的「角色 × 選單」可見性把關(由既有 Casbin 權限機制提供、選單以路由名為鍵)。本波新增**維運期編輯路徑**(設定 / 讀取某角色可見選單集),**不新增資料表、不改授權機制本身**;變更為硬替換、即時生效、跨實例一致。
- **角色落地頁(Role home)**:角色登入後的落地頁屬性;本波承既有角色資料表**新增此屬性**,預設為系統首頁;runtime 導覽據此回報使用者落地頁。
- **選單(Menu)**:承既有選單定義(選單資料表);本波**只讀用**(取有效選單供指派 + 識別碼↔路由名對映),不改其定義。

## Success Criteria *(mandatory)*

> 下列百分比指對所列舉的代表性 case 矩陣**全數通過**(各類正反例至少各一),非統計抽樣。

### Measurable Outcomes

- **SC-001**: 維運者可於角色管理頁完整設定某角色可見選單,變更 100% **即時反映**於該角色 runtime 導覽(指派的出現、移除的消失),**無需重啟**。
- **SC-002**: 可見性變更在**所有服務實例 100% 即時一致**生效(不因實例不同而看到舊可見性)。
- **SC-003**: 維運者可設定角色落地頁,該角色使用者登入後 runtime 導覽 100% 回報所設落地頁(多角色取第一有效角色);未設定者 100% 回報系統預設首頁。
- **SC-004**: 自鎖防護:會造成維運者失去「選單管理頁」本身可見性的移除 100% 被拒;批次清空命中核心導覽者 100% 整批拒、0% 部分執行。
- **SC-005**: 編輯授權正確:最高權限者(Super)成功率 100%,其他已認證使用者與未認證請求被拒比例 100%(0% 越權編輯)。
- **SC-006**: 可見性變更與落地頁變更 100% 記錄稽核(操作者 + 變更前後集 / 更新時間,成對)。
- **SC-007**: 既有能力於本波改動後 100% 不被破壞(回歸):未編輯時 runtime 導覽逐字輸出 / 常數路由 / 選單三讀端 / 選單寫端 / 既有授權階梯維持原樣。

## Assumptions

- **沿用既有可見性把關機制**:選單可見性走既有 Casbin 權限把關(既有 menu-visibility policy);本波只加**維運期編輯路徑**,不改授權機制、不新增可見性資料表。
- **變更即時生效 + 跨實例一致**:沿既有「一致性優先」基建(既有訊息發布/訂閱機制)使可見性變更在所有實例即時生效;單一實例下亦即時。
- **硬替換、不可復原**:設定某角色可見集為取代其舊集;復原 / 保護標記 / 版本管理留後續「受管 policy 層」feature。
- **多角色落地頁取第一有效角色**(以角色識別碼順序),不另加角色優先序欄位。
- **沿用既有資料表**:選單資料表(只讀)、角色資料表(新增落地頁屬性)、既有稽核機制(§I.6 成對 + 操作稽核);選單識別碼↔路由名對映沿既有選單定義。
- **前端沿用既有角色管理頁的選單授權對話框**(menu-auth-modal,目前未接線),本波接上既有受管接線軌道,不改 form 結構 / 型別。
- **跨既有能力的觸及與回歸範圍**:本波對既有可見性把關加維運期編輯路徑 + 對角色加落地頁屬性,屬對既有讀端(導覽)的擴充 —— MUST 以回歸驗證既有導覽逐字輸出、選單讀/寫端、授權把關不被破壞(見 SC-007);wire 形狀對齊與前端送出形細節於規劃/研究階段以實際 code 與既有契約對齊(plan/research)。
