## Clarifications

### Session 2026-06-04 (Phase 0 brainstorm 親決 K1–K4)

- Q: 「全路由 enforce rollout」現況? → A: grounding 揭露**字面已完成**(所有受保護業務 API 端點皆已在既有授權把關後、零破口);本波真正交付的是「**runtime 可編輯 + 治理 + 防呆守衛**」,非「補上未把關的端點」。
- Q: endpoint 授權要不要變維運期可編輯,做到多深? → A: **是,但只做基本 runtime 編輯(K1+K2)**:沿用既有授權把關的「硬替換」機制使其維運期可編輯;**不**做「可復原 / 受保護標記 / 版本管理」那種完整受管層(留後續 feature)。
- Q: 可編輯的話,如何防「整站自鎖」? → A: **root-mode(K3)**:最高權限角色(超級管理員)**永遠擁有全部端點存取、且不可被編輯**;只有其餘角色的端點集可被編輯。如此「能編輯權限的人(超管)永遠不會被鎖出」,自鎖風險歸零。
- Q: 要不要做編輯介面(UI)? → A: **要(K4)**:在角色管理頁提供「接口權限」編輯介面(對齊既有的選單權限/按鈕權限介面),root-mode 下對超管顯示為唯讀全通、對其餘角色可編。
- Q: 唯一的矩陣分歧(選單管理讀端 = 最高權限角色限定 vs 一般管理角色亦可讀)怎麼處理? → A: **以現行實作(最高權限角色限定)為單一真相**,並更正與之矛盾的設計文件;因端點授權已可維運期編輯,是否放寬給管理角色成為**維運決定**(超管可於執行期授予),不在預設硬塞。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 維運者執行期編輯某角色可呼叫的 API 端點集,即時生效 (Priority: P1)

身為系統維運者(最高權限),我希望在執行期為某個**非最高權限**角色設定其可呼叫的 API 端點集合(硬替換),讓變更**即時反映**、無需重啟、且跨服務實例一致;最高權限角色(超級管理員)則永遠擁有全部端點存取、不可被編輯(避免把自己鎖出整個後台)。

**Why this priority**: 這是把 endpoint 授權從「建置期硬編、只能改 migration + 重新部署」變成「**維運期可編輯**」的關鍵一步,補齊授權三本柱的最後一塊(選單可見性〔前波〕、按鈕權限〔前波〕、**API 端點權限〔本波〕**)。可單獨交付(編輯某角色端點集 → 該角色人員即時可/不可呼叫對應 API)即構成價值。

**Independent Test**: 以最高權限身分為某一般角色授予/移除某 API 端點 → 以該角色人員身分呼叫該端點,授予者成功、移除者被拒(權限不足);變更後不重啟即生效;嘗試編輯最高權限角色的端點集 → 被拒(業務錯誤);期間其他角色不受影響。

**Acceptance Scenarios**:

1. **Given** 一個一般角色與一組受權限把關的 API 端點, **When** 維運者設定該角色可呼叫的端點集並儲存(硬替換), **Then** 該角色授權更新,該角色人員即時(無需重啟)可呼叫被授予的端點、不可呼叫未授予的。
2. **Given** 某一般角色已被授予某端點, **When** 維運者移除該端點並儲存, **Then** 該角色人員呼叫該端點即時被拒(權限不足),其餘授權維持不變。
3. **Given** 維運者嘗試編輯最高權限角色(超級管理員)的端點集, **When** 提交, **Then** 操作被拒(業務錯誤),超管端點集維持「全部」不變。
4. **Given** 編輯介面開啟某一般角色, **When** 載入, **Then** 該角色目前被授予的端點以勾選狀態正確預載。

---

### User Story 2 - 角色管理頁的「接口權限」編輯介面 (Priority: P2)

身為系統維運者,我希望在角色管理頁有一個「接口權限」編輯介面(對齊既有的「選單權限 / 按鈕權限」),列出所有受權限把關的可用端點清單,讓我以勾選方式設定角色的端點集;對最高權限角色顯示為「全通、唯讀」,對其餘角色可編輯。

**Why this priority**: 介面讓 US1 的能力對維運者**可用且一致**(與選單/按鈕權限同一操作範式);但它服務於 US1 的授權能力,故次要。可單獨驗證(開啟某角色介面 → 顯示端點清單與目前授權、勾選提交)。

**Independent Test**: 以最高權限身分開啟某一般角色的接口權限介面 → 顯示可用端點清單與該角色目前授權(預勾)、可勾選提交;開啟最高權限角色 → 顯示全勾且唯讀(不可編輯)。

**Acceptance Scenarios**:

1. **Given** 可用端點清單與某一般角色, **When** 維運者開啟該角色的接口權限介面, **Then** 清單完整呈現所有受把關端點、該角色目前授權以勾選狀態預載。
2. **Given** 編輯介面開啟最高權限角色, **When** 載入, **Then** 介面顯示全部端點為已授予且**唯讀/不可編輯**(對應 root-mode)。
3. **Given** 維運者於一般角色勾選一組端點, **When** 提交, **Then** 該角色授權更新並即時生效(US1)。

### User Story 3 - 全路由治理:防呆守衛 + 矩陣單一真相 (Priority: P3)

身為系統維運者/維護者,我希望有一道**自動守衛**確保「每個受權限把關的 API 端點都確實在可用端點清單內、且至少被授予一個角色」—— 使未來新增 API 端點時,若漏設權限或端點識別打錯字,會被**測試抓出來**,而非靜默變成「沒有任何角色能呼叫的死端點」;並希望授權矩陣有**單一真相**(設計文件與實際把關一致,不再有過時/矛盾的描述)。

**Why this priority**: 這是「全路由治理」的安全網與正確性保障 —— 補上現況「端點識別字串與路由註冊之間無任何自動綁定 → 打錯字靜默變死端點」的結構破口,並消除設計文件與實作矩陣的矛盾。屬安全網/佐證,優先序最低但必要。

**Independent Test**: 在不破壞既有端點的前提下,守衛驗證通過(所有受把關端點皆在清單內且至少一角色可呼叫);**故意**引入一個受把關但未登記/未授權的端點 → 守衛驗證失敗(抓出破口);設計文件與實際授權矩陣描述一致(無「規劃 X 但實作 Y」的矛盾)。

**Acceptance Scenarios**:

1. **Given** 所有受權限把關的 API 端點, **When** 跑治理守衛驗證, **Then** 每個端點皆在可用端點清單內、且至少一個角色被授權可呼叫(無死端點),有權角色(帶有效身分)呼叫得允許、無權角色被拒。
2. **Given** 一個故意未登記/未授權的受把關端點, **When** 跑守衛驗證, **Then** 驗證**失敗**並指出該端點(破口被抓)。
3. **Given** 設計文件的授權矩陣描述, **When** 對照實際把關, **Then** 兩者一致(過時的「萬用授權」規劃描述已更正為實際的逐端點授權;唯一的選單讀端分歧已以實作為準拍板統一)。

### Edge Cases

- **root-mode 自鎖防護**:任何「編輯最高權限角色端點集」的請求 MUST 被拒(業務錯誤);最高權限角色端點集恆為「全部」、不受編輯影響 → 整站自鎖風險歸零。
- **硬替換語意**:儲存某角色端點集 = 取代其舊集(非增量);本波不提供復原/版本管理。
- **即時 + 跨實例**:端點授權變更後不重啟即反映;多服務實例時所有實例即時一致。
- **非法輸入**:授予不存在/未登記的端點識別、角色不存在、非法角色識別碼 → 業務錯誤(非授權/基建類)。
- **未認證 / 越權編輯**:未認證請求與非最高權限者的編輯請求 MUST 被拒(沿既有授權把關與錯誤碼)。
- **守衛的「帶身分」前提**:治理守衛驗證「未授權被拒」時 MUST 以**已認證但無權**的身分驗證(403/權限不足),而非未認證請求(未認證會在授權檢查之前即被擋、會遮蔽「漏授權」破口)。
- **新增端點防呆**:未來新增受把關 API 端點若未同步登記進可用端點清單 / 未授予任一角色 → 守衛驗證 MUST 失敗(防靜默死端點)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供「角色 × API 端點權限」的**維運期編輯**能力:維運者可設定某**非最高權限**角色可呼叫的端點集合(硬替換),寫入既有授權把關;變更 MUST **即時反映**(無需重啟)且 MUST 在所有服務實例即時一致生效。
- **FR-002**: 系統 MUST 提供讀取某角色目前可呼叫端點集的能力(供編輯介面預載勾選狀態);讀取最高權限角色時 MUST 回報「全部端點」。
- **FR-003**: 系統 MUST 維護一份**可用端點清單(registry)**= 所有受權限把關的 API 端點(以端點識別〔資源 + 操作〕為鍵),作為編輯與治理的**單一真相**;清單 MUST 涵蓋本波新增的權限編輯端點自身。
- **FR-004**: 系統 MUST 實施 **root-mode**:最高權限角色(超級管理員)MUST 永遠擁有全部端點存取且 MUST NOT 可被編輯;對「編輯目標為最高權限角色」的請求 MUST 以業務錯誤拒絕。其餘角色的端點集 MUST 可被編輯。
- **FR-005**: 系統 MUST 於角色管理頁提供「接口權限」編輯介面(對齊既有選單/按鈕權限介面範式):列出可用端點清單、預載該角色目前授權;對最高權限角色 MUST 顯示為全通且唯讀,對其餘角色 MUST 可勾選編輯並提交。
- **FR-006**: 系統 MUST 提供**治理守衛**(自動化驗證):驗證每個受權限把關的 API 端點皆在可用端點清單內、且至少被授予一個角色可呼叫(無死端點);驗證 MUST 能抓出「受把關但未登記/未授權」的端點;驗證「無權被拒」時 MUST 以已認證但無權的身分進行(非未認證請求)。(註:守衛的 coverage 驗證〔registry/授權一致性〕可由建置期靜態檢查滿足、不必發送請求;「有權允許/無權被拒」的 runtime 語意則由 acceptance 的「已認證但無權身分」case 覆蓋 —— 二者分流。)
- **FR-007**: 系統 MUST 使授權矩陣達成**單一真相**:更正設計文件中與實作矛盾的過時授權描述(過時的「萬用授權」規劃 → 對齊實際的逐端點授權);唯一的選單讀端分歧 MUST 以現行實作(最高權限角色限定)為準拍板統一、文件對齊。
- **FR-008**: 端點權限編輯 MUST 限最高權限管理員(超級管理員)存取;其他已認證使用者 MUST 被拒(權限不足),未認證請求 MUST 被拒(沿既有授權把關與錯誤碼)。
- **FR-009**: 業務驗證錯誤(非法/未登記端點識別、編輯最高權限角色、角色不存在、非法識別碼)MUST 以既有「業務錯誤」碼回應(非授權/基建類);回傳沿既有統一回應格式與對外字串識別碼契約。
- **FR-010**: 既有能力 MUST NOT 因本波而被破壞(回歸):既有端點授權矩陣(各角色現有可呼叫端點)、所有受把關路由的把關行為、既有授權階梯(未認證/無權/有權的回應碼)、選單與按鈕權限編輯、選單/角色/用戶讀寫端 MUST 維持原行為。唯一 intended 變更為:選單讀端分歧的文件對齊(實作不變)。
- **FR-011**: 端點權限變更 MUST 記錄稽核中介資料(操作者 + 變更前後集)。
- **FR-012**: 本波 MUST NOT 包含:端點授權的復原(restore)/ 版本管理 / 受保護標記等「完整受管層」(留後續 feature);授權把關機制本身的重寫(如改為萬用/前綴比對);既有「於請求處理內自驗身分」的端點(登入資訊/動態路由/路由存在性查詢)之把關方式統一;授權把關不新增資料表、不改寫底層授權儲存元件。

### Key Entities *(include if feature involves data)*

- **端點權限(Endpoint permission)**:角色 × API 端點(資源 + 操作)的授權,由既有授權把關機制提供。本波新增**維運期編輯路徑**(設定/讀取某角色可呼叫端點集);**不新增資料表、不改授權機制本身**;變更為硬替換、即時生效、跨實例一致。
- **可用端點清單(Endpoint registry)**:所有受權限把關的 API 端點之集合(以端點識別為鍵),作為編輯與治理守衛的單一真相;承既有授權把關,不新增資料表。
- **角色(Role)**:最高權限角色(超級管理員)= root,恆全通、不可編輯;其餘角色的端點集可編輯。承既有角色資料。
- **治理守衛(Coverage guard)**:自動化驗證機制,綁定「受把關端點 ⊆ 可用端點清單 ⊆ 已授權」三者一致,抓出漏登記/漏授權/識別字打錯的破口。

## Success Criteria *(mandatory)*

> 下列百分比指對所列舉的代表性 case 矩陣**全數通過**(各類正反例至少各一),非統計抽樣。

### Measurable Outcomes

- **SC-001**: 維運者可於角色管理頁完整設定某非最高權限角色可呼叫的端點集,變更 100% **即時反映**(授予的可呼叫、移除的被拒)於該角色人員,**無需重啟**。
- **SC-002**: 端點授權變更在**所有服務實例 100% 即時一致**生效(不因實例不同而看到舊授權)。
- **SC-003**: root-mode 正確:最高權限角色 100% 擁有全部端點存取;對其編輯的請求 100% 被拒(0% 可改超管端點集)→ 自鎖事件 0 起。
- **SC-004**: 治理守衛有效:所有受把關端點 100% 在可用端點清單內且至少一角色可呼叫(0 死端點);**故意引入**的未登記/未授權端點 100% 被守衛抓出。
- **SC-005**: 矩陣單一真相:設計文件的授權矩陣描述與實際把關 100% 一致(0 處「規劃 X 但實作 Y」矛盾;選單讀端分歧已統一)。
- **SC-006**: 編輯授權正確:最高權限者成功率 100%,其他已認證使用者與未認證請求被拒比例 100%(0% 越權編輯);變更 100% 記錄稽核(操作者 + 變更前後集)。
- **SC-007**: 回歸:既有端點授權矩陣、所有受把關路由把關行為、授權階梯、選單/按鈕權限編輯、選單/角色/用戶讀寫端 100% 維持原行為(唯一 intended 變更 = 選單讀端分歧的文件對齊、實作不變)。

## Assumptions

- **沿用既有授權把關機制**:端點權限走既有授權把關(既有 RBAC policy,以「角色 × 端點識別」為鍵);本波只加**維運期編輯路徑**,不改授權機制、不新增資料表、**不改寫/分叉底層授權儲存元件**(基本硬替換沿用既有可行模式,如同前波選單/按鈕權限)。
- **變更即時生效 + 跨實例一致**:沿既有「一致性優先」基建(既有訊息發布/訂閱失效通知)使端點授權變更在所有實例即時生效;單一實例下亦即時。
- **硬替換、不可復原**:設定某角色端點集為取代其舊集;復原/受保護標記/版本管理留後續 feature(完整受管層)。
- **root-mode(自鎖防護)**:最高權限角色恆全通、不可編輯 → 只有「能編輯權限者」永不被鎖出,自鎖風險歸零,無需額外的「受保護端點」名單。
- **端點識別以「資源 + 操作」為鍵**:端點無天然數值 id,編輯與把關以端點識別(API 資源 + 操作動詞)為穩定鍵。
- **編輯介面為新增**:角色管理頁現有「選單權限 / 按鈕權限」介面,**無**接口權限介面;本波新增同範式的接口權限介面(屬既有受管前端接線軌道的擴展,確切授權邊界於規劃階段拍定)。
