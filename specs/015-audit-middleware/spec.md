## User Scenarios & Testing *(mandatory)*

### User Story 1 - 已認證請求留下存取軌跡 (Priority: P1)

身為系統維運者,我希望每一筆「已通過身分驗證」的後端請求都留下一筆存取紀錄(誰、何時、從哪個來源、打哪個介面、結果如何),以便日後稽核「某使用者何時存取過什麼」。

**Why this priority**: 這是本 feature 的核心觀察性價值 —— 沒有它,系統對「已認證活動」零可視性。單獨交付即構成一個可用的稽核基礎(access log),其餘故事都建立在它先備好的請求脈絡之上。

**Independent Test**: 以有效身分打一個受保護介面(如取得使用者資訊),查存取紀錄表恰多一筆,內容含操作者、方法、路徑、狀態碼、來源 IP、來源地;打公開介面 / 健康檢查則不留紀錄。

**Acceptance Scenarios**:

1. **Given** 一個帶有效憑證的請求, **When** 它打中任一受保護介面, **Then** 系統留下恰一筆存取紀錄,含操作者身分、請求方法/路徑、回應狀態碼、來源 IP、來源地、轉送鏈、追蹤碼、時間。
2. **Given** 一個公開介面(常數路由 / 登入本身)或健康檢查請求, **When** 它被處理, **Then** 系統**不**留存取紀錄。
3. **Given** 一個認證失敗(憑證過期/缺失)的請求, **When** 它被拒, **Then** 系統**不**留存取紀錄(只記成功認證者)。

---

### User Story 2 - 登入嘗試成敗皆留證 (Priority: P2)

身為安全稽核者,我希望每一次登入嘗試(無論成功或失敗)都被記錄,以建立登入行為軌跡,並為日後「帳號/IP 連續失敗鎖定」提供資料。

**Why this priority**: 登入是最敏感的入口;成敗皆記是安全稽核與未來防爆破鎖定的資料基礎。可獨立於 US1 驗證(不同觸發、不同紀錄表)。

**Independent Test**: 以正確密碼登入 → 登入嘗試表多一筆「成功」(帶操作者);以錯誤密碼登入 → 多一筆「失敗」(帶被嘗試帳號名、無操作者)。

**Acceptance Scenarios**:

1. **Given** 正確帳密, **When** 使用者登入, **Then** 留一筆登入嘗試紀錄:成功旗標為真、帶操作者身分、來源 IP、來源地、追蹤碼、時間。
2. **Given** 錯誤密碼, **When** 使用者嘗試登入, **Then** 留一筆登入嘗試紀錄:成功旗標為假、帶「被嘗試的帳號名」、無操作者身分。
3. **Given** 一段時間內多筆登入嘗試, **When** 依「帳號名 + 時間」或「IP + 時間」查詢, **Then** 能算出該帳號/IP 在該時窗內的失敗次數(支援未來鎖定功能)。

---

### User Story 3 - 紀錄帶可信的來源脈絡 (Priority: P3)

身為稽核資料的使用者,我希望每筆紀錄都帶可信的「從哪裡來、可關聯」脈絡 —— 真實來源 IP、原始轉送鏈、來源地、單請求追蹤碼 —— 讓紀錄真正有用、可交叉關聯。

**Why this priority**: 脈絡的「忠實與正確」決定紀錄價值(IP 寫真值、轉送鏈逐字保存、來源地由直連 IP 解析、追蹤碼可關聯)。它橫跨 US1/US2,作為 P3 是因為其價值依附於前兩個故事已在留紀錄。

**Independent Test**: 對 US1/US2 留下的任一筆紀錄,查驗:IP 欄是可當 IP 過濾的真值(非占位/錯誤)、帶轉送 header 時轉送鏈欄有逐字值、來源地非空、追蹤碼存在。

**Acceptance Scenarios**:

1. **Given** 一個直連請求, **When** 系統記錄它, **Then** 來源 IP 欄存「直連對端 IP」的真值(可當 IP 查詢)、來源地由**該直連 IP** 解析(非由轉送鏈推算)。
2. **Given** 一個帶轉送 header 的請求, **When** 系統記錄它, **Then** 轉送鏈欄逐字保存原始 header 字串;無該 header 時此欄為空。
3. **Given** 任一請求, **When** 系統記錄它, **Then** 帶一個單請求追蹤碼(若入站帶請求識別 header 則沿用、否則自動生成)。

---

### Edge Cases

- **來源地無法解析**:來源 IP 解析來源地失敗(理論上的異常輸入)→ 來源地留空、**不**阻斷紀錄寫入(best-effort)。
- **開發/容器環境私有 IP**:直連對端為私有/容器網段 IP → 來源地解析仍回非空指示(內網標記),非空值在開發環境即成立。
- **紀錄寫入失敗**:稽核紀錄寫入失敗時,**業務請求仍須成功**,失敗僅進維運 log、不外露給呼叫端。
- **公開 vs 受保護邊界**:登入介面本身、常數路由、健康檢查不留存取紀錄;唯成功認證的請求才留。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 對每一筆「成功通過身分驗證」的請求留下恰一筆存取紀錄,內容含:操作者身分、請求方法、請求路徑、回應狀態碼、來源 IP、來源地、轉送鏈、追蹤碼、建立時間。
- **FR-002**: 系統 MUST NOT 對公開/未認證介面(常數路由、登入介面本身)或健康檢查留存取紀錄;認證失敗的請求亦 MUST NOT 留存取紀錄。
- **FR-003**: 系統 MUST 以「best-effort 觀察」對待存取紀錄與登入嘗試紀錄的寫入 —— 寫入失敗時,原業務請求 MUST 仍成功,失敗僅記入維運 log、絕不外露給呼叫端(觀察性、非交易)。
- **FR-004**: 系統 MUST 對每一次登入嘗試(成功與失敗皆然)留下恰一筆登入嘗試紀錄,內容含:被嘗試的帳號名、成功/失敗旗標、操作者身分(成功時)、來源 IP、來源地、轉送鏈、追蹤碼、建立時間。由登入介面負責寫入(唯它知道業務層的成敗)。
- **FR-005**: 系統 MUST 為每筆請求擷取請求脈絡:(a) 直連對端來源 IP(永遠有值、忠實);(b) 原始轉送 header 逐字保存(未帶時為空);(c) 由來源 IP 解析的來源地;(d) 單請求追蹤碼(入站帶請求識別 header 則沿用、否則生成)。
- **FR-006**: 系統 MUST 僅由**直連來源 IP** 解析來源地,MUST NOT 解析轉送鏈以推算「真實 client」(本 feature 不做信任代理逐跳推算)。
- **FR-007**: 系統 MUST 將來源 IP 存為真實、可查詢的網路位址值(可當 IP 過濾),非占位或失敗值。
- **FR-008**: 登入嘗試紀錄 MUST 可被查詢以回答「某帳號 / 某 IP 在某時窗內失敗幾次」,以支援未來「帳號鎖定」功能(本 feature 提供資料與支援此查詢的索引,不含鎖定本身的執行)。
- **FR-009**: 兩組稽核紀錄 MUST 為 append-only:每筆紀錄是不可變事件,應用程式絕不更新或刪除既有紀錄。
- **FR-010**: 稽核紀錄的儲存結構 MUST 於環境啟動時由既有的「自動套用結構」步驟備妥,非由應用服務在執行期自行建立。
- **FR-011**: 於部署/正式環境,來源地解析 MUST 持續可用(來源地解析所需的參照資料須隨部署存在於執行環境中)。

### Key Entities *(include if feature involves data)*

- **存取紀錄(Access Log Entry)**:每一筆成功認證請求對應一筆不可變紀錄。屬性:操作者身分、請求方法、請求路徑、回應狀態碼、來源 IP、來源地、轉送鏈、追蹤碼、建立時間。append-only。
- **登入嘗試紀錄(Login Attempt Entry)**:每一次登入嘗試對應一筆不可變紀錄。屬性:被嘗試的帳號名、成功旗標、操作者身分(成功時)、來源 IP、來源地、轉送鏈、追蹤碼、建立時間。append-only;以「帳號名 + 時間」與「IP + 時間」支援時窗失敗次數查詢。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的成功認證請求各留下恰一筆存取紀錄;公開路由 / 健康檢查 / 認證失敗請求留下存取紀錄的比例為 0%。
- **SC-002**: 每一次登入嘗試(成功與失敗)各留下恰一筆登入嘗試紀錄且成功旗標正確 —— 成功者帶操作者身分、失敗者帶被嘗試帳號名且無操作者。
- **SC-003**: 已記錄請求的來源地在所有環境皆為非空(含開發環境:私有/內網位址仍解析為非空的內網指示)。
- **SC-004**: 模擬稽核寫入失敗時,業務回應完全不受影響(業務請求正常完成並回正常結果)—— 失敗注入下業務成功率維持 100%。
- **SC-005**: 已存的來源 IP 可被當作真實 IP 值取出與過濾,且歸因於 IP 儲存的寫入失敗數為 0。
- **SC-006**: 於部署/正式執行環境,一筆已記錄請求顯示已解析的來源地(來源地參照資料存在且被消費)。

## Assumptions

- **append-only 稽核表**:兩組紀錄為不可變事件、無軟刪除/無更新。(這兩張表對 constitution §I.6 審計欄標準的處置 —— 走 append-only 例外 —— 於 `/speckit-plan` 的 Constitution Check 第 8 項判定,本 spec 不預先固化。)
- **best-effort 同步寫**:採同步 best-effort 寫入;非同步/批次寫入不在範圍(未來優化)。後台管理流量低,同步寫足夠。
- **來源地存原始字串**:來源地以解析器原始輸出字串保存,不拆解為省/市等結構欄。
- **轉送鏈逐字保存**:原始轉送 header 逐字保存;「信任代理逐跳推算真實 client」不在範圍(未來 feature)。
- **承接既有能力**:本 feature 依賴既有的統一稽核哲學(由 handler 擁有寫入)、IP→來源地解析元件(本 feature 為其首個消費者)、身分驗證/操作者識別機制。
- **不做(out of scope)**:資料變動 audit 補 operator 屬性(留後續 Phase);登入失敗鎖定本身的執行(本 feature 只供資料 + 索引);非同步/批次寫入;稽核紀錄的軟刪/清理治理(append-only;保留期清理另議);來源地拆結構欄。
- **後端純功能、無前端行為**:以服務層查驗(請求 + 資料查詢)驗收,無瀏覽器/CDP 驗收。
