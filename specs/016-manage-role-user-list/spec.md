## User Scenarios & Testing *(mandatory)*

### User Story 1 — 瀏覽與搜尋角色清單(Priority: P1)🎯 MVP

系統管理者需要在「角色管理」頁看到所有角色(角色名稱、代碼、描述、啟用狀態、建立時間),並能依角色名稱、代碼、狀態搜尋、分頁瀏覽,以管理系統的權限角色。

**Why this priority**:角色是使用者權限的基礎(使用者清單要顯示每人的角色),且角色資料結構最單純 — 先立「分頁清單 + 搜尋 + 顯示欄位 + 授權」這套可重用 pattern,使用者清單(US2)與未來 menu(017)直接沿用。

**Independent Test**:以具管理權的帳號呼叫角色清單,帶不同分頁與搜尋條件 → 查驗回傳正確的分頁角色資料(含描述/狀態/時間),搜尋條件生效、只含未刪除角色。

**Acceptance Scenarios**:

1. **Given** 系統有多個角色,**When** 管理者以預設分頁取角色清單,**Then** 回傳第一頁角色(含角色名稱/代碼/描述/狀態/建立時間)與總筆數
2. **Given** 角色清單,**When** 管理者以角色名稱關鍵字搜尋,**Then** 只回傳名稱含該關鍵字的角色
3. **Given** 角色清單,**When** 管理者依狀態(啟用/停用)篩選,**Then** 只回傳該狀態的角色
4. **Given** 一般(無管理權)使用者,**When** 嘗試取角色清單,**Then** 被拒絕(權限不足回應)、不回傳資料
5. **Given** 有角色已被刪除,**When** 取角色清單,**Then** 已刪除角色不出現於結果

---

### User Story 2 — 瀏覽與搜尋使用者清單(含其角色)(Priority: P2)

系統管理者需要在「使用者管理」頁看到所有使用者(帳號、暱稱、性別、電話、信箱、狀態、所屬角色、建立時間),並能依帳號/暱稱/電話/信箱/性別/狀態搜尋、分頁瀏覽,以管理系統使用者。

**Why this priority**:使用者管理是 admin panel 的核心問責軌跡;建立在角色清單(US1)pattern 之上,且每筆使用者需顯示其所屬角色(依賴角色資料)。

**Independent Test**:以具管理權的帳號呼叫使用者清單 → 查驗回傳分頁使用者資料、每筆含其所屬角色清單、搜尋條件生效、只含未刪除使用者。

**Acceptance Scenarios**:

1. **Given** 系統有多個使用者,**When** 管理者以預設分頁取使用者清單,**Then** 回傳第一頁使用者(含帳號/暱稱/性別/電話/信箱/狀態/所屬角色/建立時間)與總筆數
2. **Given** 使用者清單,**When** 管理者以帳號或暱稱關鍵字搜尋,**Then** 只回傳符合的使用者
3. **Given** 使用者清單,**When** 管理者依性別或狀態篩選,**Then** 只回傳符合的使用者
4. **Given** 某使用者具備多個角色,**When** 取使用者清單,**Then** 該使用者列含其全部所屬角色
5. **Given** 一般(無管理權)使用者,**When** 嘗試取使用者清單,**Then** 被拒絕(權限不足回應)
6. **Given** 有使用者已被刪除,**When** 取使用者清單,**Then** 已刪除使用者不出現於結果

---

### User Story 3 — 取得全部角色供選擇(Priority: P3)

管理者在編輯使用者或設定選單授權時,需要一份「全部可用角色」的輕量清單(角色識別碼 + 名稱 + 代碼)填入下拉選單,不需分頁。

**Why this priority**:輔助 US2(編輯使用者選角色)與未來選單授權;為輕量唯讀資料,獨立可驗。

**Independent Test**:以具管理權的帳號呼叫全部角色清單 → 查驗回傳所有未刪除角色的輕量資料(識別碼/名稱/代碼),不分頁。

**Acceptance Scenarios**:

1. **Given** 系統有多個角色,**When** 管理者取全部角色,**Then** 回傳所有未刪除角色的輕量清單(識別碼 + 名稱 + 代碼)、不分頁
2. **Given** 一般(無管理權)使用者,**When** 嘗試取全部角色,**Then** 被拒絕(權限不足回應)

---

### Edge Cases

- **空搜尋條件**:搜尋欄留空(空字串/未提供)→ 視為不套用該篩選(回全部符合),不報錯。
- **單頁筆數過大**:請求單頁筆數超過上限 → 夾到上限值(避免一次取過多)。
- **無權存取**:不具管理權的角色存取這 3 條 → 一律拒絕(權限不足回應),不洩漏資料。
- **無效/缺憑證**:無憑證或憑證失效 → 視為未認證(要求重新登入),不回資料。
- **使用者無角色**:某使用者未指派任何角色 → 其角色清單為空陣列(非錯誤)。
- **缺值顯示欄**:選填欄位(性別/電話/信箱/描述/更新時間)無值 → 回空值,不阻斷清單。
- **操作者欄**:建立者/修改者顯示名於本 feature 暫為空(操作者歸屬折後續 Phase)。

## Requirements *(mandatory)*

### Functional Requirements

**角色清單(US1)**

- **FR-001**:系統 MUST 提供角色清單查詢,支援分頁,並可依角色名稱、角色代碼(關鍵字)、狀態(等值)篩選;每筆回角色名稱、角色代碼、描述、狀態、建立時間、更新時間。
- **FR-002**:系統 MUST 提供「全部角色」輕量查詢(不分頁),回所有有效角色的識別碼、角色名稱、角色代碼。

**使用者清單(US2)**

- **FR-003**:系統 MUST 提供使用者清單查詢,支援分頁,並可依帳號、暱稱、電話、信箱(關鍵字)、性別、狀態(等值)篩選;每筆回帳號、暱稱、性別、電話、信箱、狀態、所屬角色清單、建立時間、更新時間。
- **FR-004**:使用者清單每筆 MUST 含該使用者所屬的角色清單(以角色代碼表示);無角色者回空清單。

**授權(US1/US2/US3 共用)**

- **FR-005**:這 3 條查詢 MUST 受角色授權保護 —— 具管理權的角色(對齊既有 RBAC 種子:超管/admin)可存取;不具權的角色 MUST 被拒絕(權限不足回應);無/失效憑證 MUST 視為未認證。

**顯示欄位補齊**

- **FR-006**:系統 MUST 補齊角色與使用者的管理顯示欄位(角色:描述、狀態、建立/更新時間;使用者:狀態、性別、電話、信箱、建立/更新時間),使清單呈現完整且可搜尋,既有種子資料須有合理預設(狀態預設為「啟用」)。

**查詢契約 / 範圍**

- **FR-007**:清單查詢 MUST 只回未刪除(active)的資料。
- **FR-008**:分頁 MUST 回「資料列 + 當前頁碼 + 單頁筆數 + 總筆數」契約(對齊前端既有分頁型);未指定時用合理預設(第 1 頁、預設筆數);單頁筆數 MUST 設上限保護(超過則夾到上限)。
- **FR-009**:空白搜尋條件 MUST 視為不套用該篩選(回全部符合);搜尋 MUST 以安全參數化方式建構查詢(不得以字串拼接使用者輸入)。

**契約守恆 / 範圍**

- **FR-010**:回應 MUST 沿用既有統一回應信封;識別碼 MUST 以數值型呈現,對齊前端型別宣告。
- **FR-011**:本 feature MUST NOT 破壞既有行為(既有測試、回應信封、登入/認證、資料存取邊界、健康檢查、系統啟動不自行套用結構變更)。
- **FR-012**:本 feature MUST NOT 引入:選單清單/選單樹/可用頁面清單(menu 三件,後續 017)、寫入操作(新增/修改/刪除角色或使用者)、操作者歸屬(誰建立/修改)、使用者頭像、多租戶 domain、非同步/批次查詢。

### Key Entities

- **角色清單項(role list item)**:一個角色的管理視圖 —— 識別碼、角色名稱、角色代碼、描述、狀態、建立/更新時間。
- **使用者清單項(user list item)**:一個使用者的管理視圖 —— 識別碼、帳號、暱稱、性別、電話、信箱、狀態、所屬角色清單、建立/更新時間。
- **清單查詢條件(list query)**:分頁(頁碼/單頁筆數)+ 各搜尋欄位(關鍵字 / 等值);空欄位視為不篩選。
- **分頁結果(paginated result)**:資料列 + 當前頁碼 + 單頁筆數 + 總筆數。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**:管理者能在角色清單以分頁 + 搜尋(名稱/代碼/狀態)取得角色,每筆含描述/狀態/時間(可驗:帶不同條件各驗)。
- **SC-002**:管理者能在使用者清單以分頁 + 搜尋取得使用者,每筆含其所屬角色清單(可驗:多角色使用者驗角色齊全)。
- **SC-003**:管理者能取得「全部角色」輕量清單供下拉選用(可驗)。
- **SC-004**:不具管理權的角色存取這 3 條被拒絕(權限不足回應);無/失效憑證視為未認證(可驗:一般角色 + 缺憑證各驗)。
- **SC-005**:清單只含未刪除資料;分頁契約正確(資料列/頁碼/筆數/總數),單頁筆數超過上限時被夾到上限(可驗)。
- **SC-006**:識別碼以數值型呈現、狀態/性別以前端列舉值呈現,與前端型別宣告一致(可驗:對照前端 typing)。
- **SC-007**:套用本 feature 後,既有系統行為(既有測試、回應信封、登入/認證、資料存取邊界、健康檢查)不被破壞(可驗)。

## Assumptions

- **設計決策已凍結**:brainstorm D1-D14(2026-05-30 user 親決),見 [`docs/superpowers/016-manage-role-user-list.md`](../../docs/superpowers/016-manage-role-user-list.md);本 feature 忠實落地。
- **承接既有**:統一回應信封、軟刪除(只回 active)、授權中介層(具管理權角色 allow、無權 deny)、結構變更經既有自動套用機制 —— 皆承自前序 feature(008/009/013/010);本 feature 重用、不重造。
- **前端型別宣告為對外契約權威**:清單欄位、分頁契約、識別碼型(數值)、狀態/性別列舉值皆以 base-web 既有型別宣告為準(base-web 權威紀律)。
- **識別碼數值型(覆寫先前拍板)**:識別碼以數值型呈現,對齊前端型別宣告;先前「識別碼回字串」拍板源於 mock 行為,實測前端無處硬依賴字串型 → 改為數值。spec/plan 階段記為 Deviation,評估是否更新設計權威文件。**例外**:登入後身分查詢的使用者識別碼維持字串(既有約定、與本 feature 無關)。
- **schema 補欄交叉參照(user 授權破例)**:補欄的型/命名經 **user 授權**交叉參照既有完整後端;以**隔離方式抽取純欄位事實**(未讀其設計文件、未污染設計),前端型別宣告仍為對外契約權威、既有 codebase 慣例為實作權威。spec/plan 階段記為 Deviation。
- **活體驗收對 dev stack**:對真實服務做活體查驗(呼叫 + 資料查驗)+ 純單元測試;純後端 read、無新前端行為 → 不需瀏覽器端到端(前端端到端留 prod-stack 巡檢)。
- **既有 getUserList 示意改真實**:登入/認證 feature 曾建一個「使用者清單」示意端點(空殼),本 feature 將其改為回真實分頁資料、並改由本 feature 的清單模組提供(移除示意空殼)。

### 不在 scope

選單清單/選單樹/可用頁面清單(menu 三件,後續 017,需建選單儲存);寫入操作(新增/修改/刪除角色或使用者、批次刪除);操作者歸屬(誰建立/修改、後續 Phase A,與資料變動審計同期);使用者頭像欄;多租戶 domain;非同步/批次查詢;角色階層(父角色)、角色預設首頁路由等前端清單不需的欄位。

## Dependencies

- **008 統一回應信封**:清單回應沿用既有信封型。
- **009 軟刪除基礎設施**:清單只回 active(未刪除)資料。
- **013 認證 + 授權中介層**:3 條 endpoint 掛授權保護(具管理權角色 allow、無權 deny);承既有 RBAC 種子角色。
- **010 結構變更自動套用**:補欄與授權種子經既有自動套用機制生效。
- **base-web 既有 service 層**:這 3 條 endpoint base-web 既已宣告呼叫,本 feature 對齊其型別、不動 base-web。
