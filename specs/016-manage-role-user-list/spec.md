## User Scenarios & Testing *(mandatory)*

### User Story 1 - 使用者列表分頁查詢 (Priority: P1)

身為系統維運者(管理員),我希望進入「使用者管理」頁時能看到系統中所有使用者的分頁清單(帳號、暱稱、角色、狀態等),並能依帳號/暱稱搜尋,以便管理與稽核使用者。

**Why this priority**: 這是本 feature 的核心可見價值 —— 在此之前管理頁是空殼(後端只回 stub 空清單)。它讓 admin panel 第一次真正「看得到資料」,且立起「分頁查詢 + 輸出資料形 + 授權把關」這套後續 manage 功能共用的骨架。可單獨交付即構成一個可用的使用者管理檢視。

**Independent Test**: 以管理員身分打使用者列表介面,查得到分頁結果(含目前頁/每頁筆數/總筆數/該頁資料),每筆含帳號、暱稱、角色清單;帶搜尋條件(帳號關鍵字)時結果被正確過濾;以一般使用者身分打則被拒絕。

**Acceptance Scenarios**:

1. **Given** 一個管理員(具列表權限)身分, **When** 請求使用者列表(不帶搜尋條件、預設分頁), **Then** 回傳一頁使用者資料,含目前頁碼、每頁筆數、總筆數、該頁使用者陣列;每筆含使用者識別碼、帳號、暱稱、角色清單,且**不含密碼**。
2. **Given** 一個管理員身分, **When** 帶帳號關鍵字搜尋, **Then** 只回傳帳號含該關鍵字的使用者;搜尋條件留空時不套用該過濾(回全部)。
3. **Given** 一個管理員身分, **When** 請求超出總頁數的頁碼, **Then** 回傳空資料陣列但仍帶正確的總筆數與所請求的頁碼/每頁筆數(視為成功、非錯誤)。
4. **Given** 一個一般使用者(無列表權限)身分, **When** 請求使用者列表, **Then** 被拒絕(權限不足),不回傳任何使用者資料。
5. **Given** 一個未帶或帶無效憑證的請求, **When** 請求使用者列表, **Then** 被視為未認證而拒絕。

---

### User Story 2 - 角色列表分頁查詢 (Priority: P2)

身為系統維運者,我希望進入「角色管理」頁時能看到角色的分頁清單(角色名稱、角色代碼等),並能依名稱/代碼搜尋,以便檢視系統角色。

**Why this priority**: 與使用者列表同屬管理頁核心檢視,沿用 US1 立起的分頁查詢骨架(不同實體、相同形狀),可獨立於 US1 驗證(不同介面、不同資料表)。優先序次於 US1,因使用者管理是更高頻的維運入口。

**Independent Test**: 以管理員身分打角色列表介面,查得分頁角色清單(每筆含角色識別碼、名稱、代碼);帶名稱/代碼關鍵字搜尋時被正確過濾;一般使用者被拒。

**Acceptance Scenarios**:

1. **Given** 一個管理員身分, **When** 請求角色列表(預設分頁), **Then** 回傳一頁角色資料,含目前頁/每頁筆數/總筆數/該頁角色陣列;每筆含角色識別碼、角色名稱、角色代碼。
2. **Given** 一個管理員身分, **When** 帶角色名稱或角色代碼關鍵字搜尋, **Then** 只回傳符合的角色;條件留空時回全部。
3. **Given** 一個一般使用者身分, **When** 請求角色列表, **Then** 被拒絕(權限不足)。

---

### User Story 3 - 取得全部角色(供指派下拉) (Priority: P3)

身為操作者,我希望在「指派角色」之類的情境取得系統全部(啟用中)角色的精簡清單,以便在下拉選單中挑選。

**Why this priority**: 它是下拉選單的資料來源(被使用者/選單相關操作介面使用),非分頁、回精簡欄位(識別碼/名稱/代碼)。價值依附於前兩個列表故事,作為 P3;且其授權範圍比列表更寬(一般使用者亦可取得,供其能進入的操作介面使用)。

**Independent Test**: 任一具基本權限的登入者請求全部角色,得到一個非分頁的角色精簡清單(每筆含識別碼、名稱、代碼),只含未刪除角色。

**Acceptance Scenarios**:

1. **Given** 一個已登入者(含一般使用者), **When** 請求全部角色, **Then** 回傳非分頁的角色精簡清單(每筆只含識別碼、名稱、代碼),且只含未刪除(有效)角色。
2. **Given** 一個未帶或帶無效憑證的請求, **When** 請求全部角色, **Then** 被視為未認證而拒絕。

---

### Edge Cases

- **缺資料欄回空值**:目前資料來源尚未儲存的展示欄位(來源地、電子郵件、電話、性別、狀態、角色描述、建立/更新者與時間)→ 對應輸出欄回「空值(null)」,**不**阻斷列表回傳;此為已知狀態(預設帳號本就無這些資料)。
- **搜尋條件留空**:任一搜尋欄留空字串或不帶 → 該條件不套用(不縮減結果)。
- **每頁筆數過大**:請求每頁筆數超過上限 → 夾到上限(避免一次撈取過量),仍正常回該頁。
- **頁碼超出範圍**:請求頁碼超過總頁數 → 回空資料陣列 + 正確總筆數(成功、非錯誤)。
- **使用者無任何角色**:該使用者的角色清單回空陣列(非 null)。
- **權限不足 vs 未認證**:已認證但無權限 → 權限不足拒絕;未帶/無效憑證 → 未認證拒絕(兩者區分)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供「使用者列表」查詢能力,以分頁方式回傳使用者資料,每筆至少含:使用者識別碼、帳號、暱稱、所屬角色清單,以及前端列表既有欄位的對應位置(來源資料缺欄者回空值)。
- **FR-002**: 系統 MUST 提供「角色列表」查詢能力,以分頁方式回傳角色資料,每筆至少含:角色識別碼、角色名稱、角色代碼。
- **FR-003**: 系統 MUST 提供「全部角色」查詢能力,以非分頁清單回傳啟用中(未刪除)角色的精簡資料(識別碼、名稱、代碼)。
- **FR-004**: 分頁查詢 MUST 回傳「目前頁碼、每頁筆數、總筆數、該頁資料陣列」四項;總筆數為套用搜尋條件後、分頁前的符合總數。分頁回應形狀 MUST NOT 含額外的「總頁數」或「成功旗標」欄位。
- **FR-005**: 分頁查詢 MUST 支援頁碼與每頁筆數參數,並提供合理預設(未帶時)與每頁筆數上限(避免一次撈取過量);頁碼超出範圍時 MUST 回空資料陣列且回應為成功。
- **FR-006**: 使用者列表 MUST 支援以帳號、暱稱關鍵字過濾;角色列表 MUST 支援以角色名稱、角色代碼關鍵字過濾。任一搜尋條件留空 MUST 略過該條件(不縮減結果)。其餘前端可能送出但目前無對應資料來源的搜尋欄,MUST 被安全忽略(不報錯)。
- **FR-007**: 三個查詢 MUST 只回傳未刪除(有效)的資料列。
- **FR-008**: 使用者資料的對外輸出 MUST NOT 含密碼或任何機密欄位。
- **FR-009**: 系統 MUST 對使用者列表與角色列表施加授權把關:具管理權限的角色可存取,一般使用者 MUST 被拒(權限不足);「全部角色」查詢的授權範圍 MUST 涵蓋一般使用者(供其可進入的操作介面使用)。未認證(未帶/無效憑證)請求 MUST 一律被拒。
- **FR-010**: 對外輸出的識別碼 MUST 以**字串**形式呈現(對齊既有對外資料契約凍結值);內部資料儲存型不受此限。
- **FR-011**: 對外輸出的欄位命名與整體回應信封 MUST 對齊既有對外資料契約(信封含資料/代碼/訊息三段、代碼為字串;欄位採前端既有命名慣例);本 feature 為唯讀,正常情形回成功代碼,授權拒絕回對應的權限不足代碼。
- **FR-012**: 本 feature MUST 為唯讀,MUST NOT 包含新增/修改/刪除使用者或角色的能力,且 MUST NOT 變更前端(base-web)既有程式。

### Key Entities *(include if feature involves data)*

- **使用者(User)**:系統登入主體。本 feature 對外揭露其識別碼、帳號、暱稱、所屬角色清單;其餘展示欄位(來源地/電郵/電話/性別/狀態/建立更新者與時間)目前無來源資料,輸出回空值。不揭露密碼。只列未刪除者。
- **角色(Role)**:授權主體。對外揭露識別碼、角色名稱、角色代碼;其餘展示欄位(角色描述/狀態/建立更新者與時間)目前無來源資料,輸出回空值。只列未刪除者。
- **使用者—角色關聯**:多對多關聯,用於組出每位使用者的角色清單。列表查詢時 MUST 以批次方式取得整頁使用者的角色(避免逐筆查詢造成的效能退化)。
- **分頁結果(Paginated Result)**:列表查詢的回應外殼,含目前頁碼、每頁筆數、總筆數、該頁資料陣列四項。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員打開使用者管理頁能看到真實使用者分頁清單(取代先前的空殼),每筆顯示帳號、暱稱、角色;角色管理頁能看到真實角色分頁清單。
- **SC-002**: 100% 的列表回應符合分頁形狀(目前頁/每頁筆數/總筆數/資料陣列),且不含「總頁數」「成功旗標」欄位;對外識別碼皆為字串。
- **SC-003**: 使用者列表回應中 0% 含有密碼或機密欄位(任一筆、任一查詢條件下皆然)。
- **SC-004**: 授權把關正確:具管理權限的角色存取使用者/角色列表成功率 100%;一般使用者存取被拒比例 100%;一般使用者取得「全部角色」成功率 100%;未認證請求被拒比例 100%。
- **SC-005**: 搜尋與分頁行為正確:帶關鍵字時只回符合列,留空時回全部;頁碼超範圍回空陣列 + 正確總筆數;每頁筆數超上限被夾到上限。
- **SC-006**: 整頁使用者的角色取得不隨該頁筆數線性增加查詢次數(以批次取得,固定查詢數)。

## Assumptions

- **缺欄回空值(不動資料表)**:base-web 列表想顯示但目前資料來源未儲存的欄位(來源地/電郵/電話/性別/狀態/角色描述/建立更新者與時間),本 feature 一律於對外輸出回空值,**不**新增資料表欄位。真正儲存這些業務欄與審計欄屬日後「新增/修改使用者」功能,屆時一次補齊以避免反覆變更資料結構。(凍結 brainstorm D2;審計欄缺口見 constitution §I.6 與 CHECKLIST §2.18/§2.19,屬寫入功能那一波。)
- **對外識別碼為字串**:對齊既有對外資料契約凍結值(識別碼對外為字串),內部以整數儲存、於輸出邊界轉字串。設計文件他處殘留「數字」表述屬待清理的不一致,以凍結值字串為準。(凍結 D3。)
- **授權範圍**:使用者列表 / 角色列表 = 管理級(超管 + 管理員可、一般使用者不可);全部角色 = 含一般使用者。授權規則隨本 feature 一併備妥對應設定。(凍結 D7。)
- **唯讀、不動前端**:本 feature 只提供讀取,前端既有呼叫已存在,只需對齊回應形狀即可直接運作;前端型別宣告若與字串識別碼不符,屬另案的前端型別補正(不在本 feature)。(凍結 D10。)
- **menu 與寫入功能不在範圍**:選單相關列表(需另建選單資料表)留後續 feature;新增/修改/刪除與其它寫入端點留後續 feature。(凍結 D1 / scope。)
- **承接既有能力**:沿用既有的統一回應信封、授權把關機制、未刪除過濾邊界、資料存取的單一管道慣例。
