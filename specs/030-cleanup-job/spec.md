# Feature Specification: Refresh-Token Cleanup Job + Same-Second Login Fix

**Feature Branch**: `030-cleanup-job`

**Created**: 2026-06-06

**Status**: Draft

**Input**: User description: "@docs/superpowers/030-cleanup-job.md" — 過期 refresh-token 記錄的維運清理（純過期規則 + 安全邊際、dry-run 預設 / 明確 execute 才刪、on-demand 排程），外加修一個同秒發證會撞唯一鍵的潛在缺陷。設計來源見該 brainstorm spec-design（已拍板 4 決策）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 維運者清掉已過期的 refresh-token 記錄 (Priority: P1)

身為維護此部署的維運者，我需要一種方式把「確定已無用途」的 refresh-token 記錄實體移除，讓 token 儲存不會無限成長。為安全起見，這個工作**預設只預覽**（回報會移除幾筆、但不動任何資料），只有在我**明確要求執行**時才真的刪除。

**Why this priority**: 這是本 feature 的核心目的。前一個 token-rotation feature（027）明確把「過期/作廢憑證記錄的實體清理」延後（FR-011 OUT）。沒有它，token 儲存會無上限累積。

**Independent Test**: 在儲存中放入一批狀態各異的 token 記錄（部分已過期、部分仍有效），以預覽模式跑 → 它回報可移除筆數且不改任何資料；以執行模式跑 → 只有「確定已過期」的記錄被移除，所有仍有效的記錄（含剛用過或已作廢但尚未過期者）全數保留。

**Acceptance Scenarios**:

1. **Given** 儲存中有些記錄已過期（超過安全邊際）、有些仍在有效期內，**When** 維運者以預設**預覽模式**執行此工作，**Then** 工作回報「將移除 N 筆」且**不移除任何資料**。
2. **Given** 同上狀態，**When** 維運者以**執行模式**執行，**Then** 恰好那些「過期超過安全邊際」的記錄被移除，所有仍有效的記錄全數保留。
3. **Given** 一筆已標記為 used 或 revoked、但**尚未過期**的記錄，**When** 以執行模式執行，**Then** 該筆**保留**（讓重放偵測在它自然過期前仍有效）。
4. **Given** 一筆過期**才剛發生**（仍在安全邊際內）的記錄，**When** 以執行模式執行，**Then** 該筆**保留**（防範記錄存的過期時間與憑證本身過期時間之間的時鐘偏移）。
5. **Given** 此工作已接入部署，**When** 啟動一般應用服務，**Then** 此工作**不**隨之啟動（它是 on-demand 維運任務、由排程或人工觸發、做完即退出）。

---

### User Story 2 - 同一秒內連續登入都成功 (Priority: P2)

身為一個可能在同一秒內驗證超過一次的使用者或自動化客戶端，我的多次驗證都應該成功，而不是其中一次因內部錯誤而失敗。

**Why this priority**: 前期測試浮出一個潛在缺陷：同一秒內發出的兩個憑證會撞上唯一性限制，導致其中一次虛假失敗。真實互動使用幾乎不會觸發，但自動化 / retry 流程與測試會。修掉它消除一個真實（雖罕見）的失敗模式，並可移除一個測試 workaround。

**Independent Test**: 在同一個「一秒窗」內觸發兩次憑證發放 → 兩次都成功、無撞鍵錯誤。

**Acceptance Scenarios**:

1. **Given** 使用者在同一個一秒窗內驗證兩次，**When** 兩次驗證都被處理，**Then** 兩次都成功、儲存兩筆相異的憑證記錄（**無**唯一性限制違反）。
2. **Given** 先前測試需要刻意製造「≥1 秒間隔」才能避開撞鍵，**When** 本變更到位後，**Then** 該間隔不再需要（測試 workaround 可移除）。

---

### Edge Cases

- **沒有可移除記錄時**：工作回報 0 筆、不動資料、正常結束（成功）。
- **工作執行到一半被中斷**：移除範圍僅限「確定已過期」記錄，部分完成是安全的；剩餘符合條件者下次執行再清。
- **revoked 但未過期的記錄**：保留至自然過期（重放偵測在此期間仍有效）。
- **過期才剛發生（安全邊際內）的記錄**：保留（時鐘偏移防護）。
- **本變更部署前已在外流通的憑證**：因新增逐憑證唯一性元素、舊憑證在下次使用時會被拒、需一次性重新登入 —— 與前一次 session-id 推行的行為一致、本環境可接受。
- **未來維運憑證權限被收窄時**：工作仍透過同一個憑證參照運作（參照不變、工作不需改）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供一個 on-demand 維運任務，移除「確定已無用途」的 refresh-token 記錄。
- **FR-002**: 一筆記錄 MUST 僅在其**過期時間已過、且超過一個安全邊際（預設 60 秒）**時才被視為可移除，**與該記錄的狀態無關**。
- **FR-003**: 任務 MUST NOT 移除任何**尚未過期**的記錄（含已標記 used 或 revoked 但仍在有效期內者），以保留其自然過期前的重放偵測能力。
- **FR-004**: 任務 MUST 預設為**非破壞性的預覽模式**：回報將移除的筆數，且不修改任何資料。
- **FR-005**: 任務 MUST 僅在被以**明確的執行模式**叫用時才移除記錄。
- **FR-006**: 任務 MUST 在完成時回報受影響筆數（預覽或實移）。
- **FR-007**: 任務 MUST NOT 隨一般應用服務啟動而啟動；它由排程 / 人工 on-demand 觸發、做完即退出。
- **FR-008**: 移除操作 MUST 可安全重跑（重跑只清掉新符合條件者、否則不造成任何改變）。
- **FR-009**: 系統 MUST 確保同一個一秒窗內發出的兩個憑證被存為兩筆相異記錄、不違反憑證唯一性限制。
- **FR-010**: 為達成 FR-009 而新增的逐憑證唯一性元素 MUST NOT 改變任何對「把憑證視為不透明」之消費端可觀察的行為（不改憑證交換契約 / wire 形狀）。
- **FR-011**: 移除任務 MUST 透過一個**專用維運憑證參照**（已備妥）連線，使未來的最小權限強化不需改動此任務。
- **FR-012**: 移除任務 MUST 能在**正式部署產物**中運行（不只在開發環境），且此可運行性須經正式產物的建置與執行驗證。

### Key Entities *(include if feature involves data)*

- **Refresh-token 記錄**：一筆已發出的 refresh 憑證紀錄；具狀態（active / used / revoked）、發出時間、過期時間、使用時間戳。對清理而言關鍵屬性 = **過期時間**（清理判定的唯一依據）。彼此以一個「鏈」識別碼歸群（重放偵測撤銷整鏈用），但清理不依賴鏈或狀態。
- **已發出憑證（token）**：交給客戶端的憑證；對客戶端**不透明**；本 feature 為它加上一個**逐憑證唯一元素**，確保同一瞬間發出的兩個憑證彼此相異。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 以執行模式跑完任務後，token 儲存中**不存在**任何「過期超過安全邊際」的記錄（計數 = 0）。
- **SC-002**: token 儲存規模**有上界** —— 永遠不會留存「超過 refresh 有效窗 + 一個維運間隔」之久的記錄（非無限成長）。
- **SC-003**: 預覽模式**從不**改變儲存資料（修改筆數 = 0），以執行前後計數比對驗證。
- **SC-004**: **絕不**移除仍有效的憑證 —— 一次執行後，所有仍在有效期內的記錄（含剛用過或 revoked-但-未過期者）**100% 存活**。
- **SC-005**: 同一個一秒窗內發生的兩次驗證**兩者皆成功**（虛假失敗率 0%），而此前其中一次可能失敗。
- **SC-006**: 維運任務自行完成並退出（不殘留為常駐服務），且可重跑而無不良影響。

## Assumptions

- 維運任務由 on-demand 或外部排程（如 host 層排程器）觸發；部署**不含** in-stack scheduler。
- 一個**專用維運憑證參照已備妥**；目前具完整權限，最小權限收窄**延後**為後續工作（不阻擋本 feature）。
- **60 秒安全邊際**足以吸收「記錄存的過期時間」與「憑證本身過期時間」之間的任何偏移；移除絕不觸及任何「仍可能被驗證通過」的憑證。
- 部署逐憑證唯一性元素會使「變更前已發出」的憑證在下次使用時被拒（需一次性重新登入）—— 與前一次 session-id 推行一致、本環境可接受。
- 範圍**僅限 refresh-token 記錄**；其他 soft-deleted 資料與授權政策條目的跨表實體清理**明確排除**（被另一個 managed-RBAC 工作阻擋）。
- 本 feature **不改動**既有的 token-rotation / 重放偵測強制邏輯。
