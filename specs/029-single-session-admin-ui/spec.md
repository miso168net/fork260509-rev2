# Feature Specification: single-session admin UI（系統預設 runtime 可調 + 每帳號 policy UI）

**Feature Branch**: `029-single-session-admin-ui`

**Created**: 2026-06-06

**Status**: Draft

**Input**: User description: "single-session admin UI — 把 028 的單一-session policy 從『後端/seed/DB 設、系統預設用 config 值(改要重部署)』升級為 **admin 經 UI 控制**:系統預設 runtime 可調 + 每帳號 policy 由使用者管理頁設定。順帶把『系統設定』做成可擴充地基。設計來源:[`docs/superpowers/029-single-session-admin-ui.md`](../../docs/superpowers/029-single-session-admin-ui.md)(Phase 0 brainstorm 全決)。"

> **性質**:這是一個**管理控制面**feature —— 028 把單一-session 引擎與 policy 儲存做好了,但「開關」只能由後端設定(改系統預設要改 config 重部署、改每帳號 policy 要直接動 DB/seed)。029 讓**系統操作者(最高權限管理員)經由介面**:(a) 即時調整**全站單一-session 預設**(不必重部署);(b) 在使用者管理頁設定**每個帳號**的單一-session policy。價值在「把 028 的安全能力交到操作者手上、可日常營運」。**不改 028 的判定/踢人邏輯**——029 只改 policy 值的「來源與可調性」+ 提供操作介面。系統預設此後**以持久儲存為真相**(服務重啟仍在),並設計為可擴充的「系統設定」地基(單一-session 是第一個設定)。下列 user story 採「操作者」視角。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 操作者經 UI 即時調整全站單一-session 預設 (Priority: P1)

身為系統操作者,我希望在一個**系統設定介面**就能把「全站單一-session 預設」開或關,**不必改設定檔重新部署**;改完之後對後續請求**立即生效**。如此一來,要全站收斂登入(或恢復多裝置)時,我能即時操作,而不是排一次部署。

**Why this priority**: 這是本 feature 的核心營運價值 —— 把 028 那個「只能改 config 重部署」的全站開關變成 runtime 可調。單獨交付即讓操作者能即時控制全站預設,是 MVP。

**Independent Test**: 以授權操作者登入設定頁,把全站預設由「關」改「開」;確認設定頁顯示新值、且一個原本(預設關)多裝置並存的帳號在下一個請求起收斂為單一登入 —— 全程無服務重啟。

**Acceptance Scenarios**:

1. **Given** 全站預設目前為「關」, **When** 授權操作者在設定頁把它改為「開」並儲存, **Then** 設定頁反映新值,且後續請求依「開」判定(無需重啟)。
2. **Given** 全站預設剛被改為「開」, **When** 一個 policy=繼承、原本在多處並存的帳號發出後續請求, **Then** 該帳號收斂為「僅最新登入有效」(舊裝置被登出)。
3. **Given** 全站預設為「開」, **When** 操作者改回「關」, **Then** 後續繼承帳號恢復多裝置並存。

---

### User Story 2 - 操作者在使用者管理頁設定每帳號 policy (Priority: P1)

身為系統操作者,我希望在**使用者管理頁**看到每個帳號目前的單一-session policy,並能直接把某帳號設為**繼承 / 強制開 / 強制關**;改完**立即對該帳號生效**。如此一來,我能只對需要的帳號收斂登入,而不必動 DB。

**Why this priority**: 與 US1 同列 P1 —— 028 的「per-account 可控」必須要有 per-account 的 UI 入口才算可營運;否則每帳號 policy 仍得手動改 DB。

**Independent Test**: 在使用者管理頁對某帳號(原本多處並存)用「設定單一-session」操作設為「開」;確認該帳號在下一個請求起收斂為單一登入、其他帳號不受影響。

**Acceptance Scenarios**:

1. **Given** 使用者管理頁列出帳號, **When** 操作者檢視某帳號, **Then** 顯示其目前的單一-session policy(繼承/開/關)。
2. **Given** 某帳號 policy 為「繼承」且原本多處並存, **When** 操作者把它設為「開」並儲存, **Then** 該帳號於後續請求收斂為單一登入,且**該變更立即生效**(不被既有快取狀態遮蔽)。
3. **Given** 操作者改了甲帳號的 policy, **When** 乙帳號發出請求, **Then** 乙不受影響(帳號間隔離)。
4. **Given** 某帳號 policy 為「開」, **When** 操作者把它設回「繼承」或「關」, **Then** 該帳號恢復依繼承值/多裝置並存。

---

### User Story 3 - 只有授權操作者能檢視/變更這些控制 (Priority: P2)

身為系統的安全守護者,我希望「系統設定」與「每帳號單一-session policy」這些控制**只有最高權限管理員**能看到與變更;一般使用者**看不到設定入口、也無法變更任何 policy**。如此一來,這個影響全站安全姿態的開關不會被越權操作。

**Why this priority**: 直接決定 US1/US2 能不能安全開放 —— 把全站/帳號的登入收斂交給未授權者是不可接受的風險。P2(US1/US2 的必要配套)。

**Independent Test**: 以非授權帳號嘗試開設定頁/呼叫變更 → 被拒(看不到選單、變更被擋);以授權操作者則可正常檢視與變更。

**Acceptance Scenarios**:

1. **Given** 一個非最高權限的使用者, **When** 它嘗試進入系統設定頁或變更某帳號 policy, **Then** 被拒(設定選單不可見、變更請求不被授權)。
2. **Given** 一個最高權限操作者, **When** 它檢視/變更設定或每帳號 policy, **Then** 正常完成。

---

### User Story 4 - 變更立即且正確生效、不誤傷正常使用 (Priority: P2)

身為操作者,我希望我做的任一變更(全站預設或某帳號 policy)在**下一個請求就正確反映**,不會卡在舊狀態;同時**啟用單一-session 不會把正常單一使用的人誤踢**(包含長時間使用、憑證背景換新)。

**Why this priority**: 確保 029 的控制是「可信賴的開關」而非「改了不知道有沒有生效」。P2(US1/US2 的正確性邊界)。

**Independent Test**: 改某帳號 policy=開後,該帳號被收斂;但一個只在一處正常使用(含背景換新)的啟用帳號,跨越憑證換新後仍始終有效、不被誤踢。

**Acceptance Scenarios**:

1. **Given** 操作者把某帳號 policy 設為「開」, **When** 該帳號下一個受保護請求發生, **Then** 立即依「開」判定(不被舊快取狀態遮蔽)。
2. **Given** 一個啟用單一-session 的帳號只在一處正常使用, **When** 其憑證隨時間自動換新後繼續操作, **Then** 始終有效、不被誤踢。

---

### User Story 5 - 變更可被稽核追溯 (Priority: P3)

身為系統的稽核需求方,我希望每一次「系統設定變更」或「每帳號 policy 變更」都被**記錄是誰、改了什麼**,以便事後追溯安全姿態的調整。

**Why this priority**: 安全敏感控制的可追溯性;非新功能能力、屬營運稽核配套,優先序最低。

**Independent Test**: 操作者變更全站預設與某帳號 policy 後,於操作稽核紀錄查得對應的「誰、何時、改了哪個設定/帳號」事件。

**Acceptance Scenarios**:

1. **Given** 操作者變更了全站預設, **When** 查稽核紀錄, **Then** 有一筆可歸因到該操作者的設定變更事件。
2. **Given** 操作者變更了某帳號 policy, **When** 查稽核紀錄, **Then** 有一筆可歸因到該操作者、指明目標帳號與新值的事件。

### Edge Cases

- **開啟時的多裝置收斂**:操作者把全站預設(或某帳號)由「關」改「開」時,受影響且原本多裝置並存的帳號於後續請求收斂為單一登入(最新登入有效、舊裝置被登出);**當前最新 session 不被誤踢**。介面宜提示此後果。
- **變更的即時性 vs 既有快取**:每帳號 policy 變更後,**不得**因既有的熱路徑快取而沿用舊 policy;變更須在該帳號下一個請求即生效。
- **持久性**:全站預設以持久儲存為真相,**服務重啟後仍為操作者最後設定的值**;持久儲存於開機不可達時退回安全預設(關),服務仍能啟動。
- **非法值**:對某設定給出值域外的值(例如全站預設非「開/關」)→ 變更被拒、原值不變。
- **帳號間隔離**:對某帳號的 policy 變更絕不影響其他帳號。
- **越權**:非授權者既看不到設定入口、變更請求也被擋(雙重)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓授權操作者經由管理介面設定**全站單一-session 預設**(套用於 policy=繼承之帳號的預設值),且**不需重新部署**即可變更。
- **FR-002**: 全站預設的變更 MUST 在**後續受保護請求即生效**,**不需服務重啟**。
- **FR-003**: 系統 MUST 讓授權操作者在**使用者管理頁**設定**每個帳號**的單一-session policy(繼承 / 強制開 / 強制關)。
- **FR-004**: 每帳號 policy 的變更 MUST 在**該帳號下一個受保護請求即生效**,且 MUST NOT 被任何既有狀態快取遮蔽(變更後不得沿用變更前的判定)。
- **FR-005**: 系統 MUST 向操作者**顯示**目前的全站預設,以及使用者管理頁中**每個帳號目前的 policy**(讓操作者在變更前可見現狀)。
- **FR-006**: 只有**最高權限管理員角色**MUST 能檢視或變更全站預設與每帳號 policy;未授權者 MUST NOT 看到設定入口、亦 MUST NOT 能變更任何 policy(選單可見性 + 變更授權雙重把關)。
- **FR-007**: 對全站預設或每帳號 policy 的每一次變更 MUST 寫入既有的操作稽核紀錄(可歸因到操作者、指明目標與新值)。
- **FR-008**: 啟用單一-session(全站或某帳號)MUST 使受影響且多裝置並存的帳號於後續請求**收斂為單一有效登入**(沿 028 既有判定);停用 MUST 恢復多裝置並存。**029 MUST NOT 改變 028 既有的踢人/放行判定邏輯**——僅改變 policy 值的來源與可調性。
- **FR-009**: 全站預設值 MUST **持久**(服務重啟後仍為操作者最後設定的值);持久儲存於開機不可達時 MUST 退回安全預設、服務仍能啟動。
- **FR-010**: 029 對既有 wire 契約的變更 MUST **僅限**「使用者列表回應**增加**每帳號 policy 欄位」一處;MUST NOT 變更任何其他既有端點的請求/回應結構。
- **FR-011**: 每帳號 policy MUST 為三態之一:**繼承 / 強制開 / 強制關**(沿 028 模型);「繼承」解析為當前全站預設。
- **FR-012**: 全站預設於從未被操作者設定前 MUST 為**停用(關)**(沿 028 dormant 姿態)。
- **FR-013**: 對某設定給出值域外的值 MUST 被拒絕,且 MUST NOT 改動原值。
- **FR-014**: 本 feature MUST NOT 實作:動態 metadata 驅動的設定 UI、單一-session 以外的其他系統設定(本 feature 只暴露全站單一-session 預設一個設定)、或「每裝置一個 session」(沿 028 FR-013、仍 OUT)。

### Key Entities *(include if feature involves data)*

- **全站單一-session 預設(system-wide default)**:一個可由操作者調整、**持久**、且後續請求即時讀到的值,決定 policy=繼承之帳號的單一-session 行為。為可擴充「系統設定」能力的第一個設定。
- **每帳號單一-session policy(per-account policy)**:某帳號的三態值(繼承 / 開 / 關),由操作者設定;決定該帳號是否套用 028 的登入收斂。
- **設定變更稽核事件(setting-change audit record)**:一次設定/policy 變更的紀錄 —— 誰、何時、改了哪個設定或哪個帳號、新值為何。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 操作者能於 UI 把全站單一-session 預設開/關,並在**下一個請求**看到判定依新值,**0 次**服務重啟。
- **SC-002**: 操作者能於使用者管理頁設定任一帳號的 policy,該變更於該帳號**下一個請求**即生效(數秒內),**0 次**被舊快取遮蔽。
- **SC-003**: 未授權(非最高權限)使用者**100%** 無法看到或變更這些控制(**0 次**越權變更成功)。
- **SC-004**: 全站預設/每帳號 policy 的每一次變更**100%** 寫入操作稽核紀錄、可歸因到操作者。
- **SC-005**: 對一個多裝置並存帳號啟用單一-session 後,於後續請求**100%** 收斂為恰一個有效 session;對正常單一使用(含跨憑證換新)的啟用帳號造成 **0 次**誤登出。
- **SC-006**: 既有端點/回應與升級前 **0 差異**,唯一例外為使用者列表**新增**每帳號 policy 欄位。
- **SC-007**: 全站預設值於服務重啟後 **100%** 仍為操作者最後設定的值(持久);持久儲存不可達時以安全預設(關)啟動。

## Assumptions

- **承 028 引擎**:028 single-session enforcement(引擎 + policy 儲存)已落地;029 只加「操作者可調的 policy 來源 + 介面」,不改 028 的判定/踢人邏輯。
- **沿 028 policy 模型**:每帳號三態(繼承/開/關)+ 全站預設「關」(dormant)沿用 028 既有語義。
- **系統設定地基**:全站單一-session 預設是一個可擴充「系統設定」能力的第一個設定;未來新增系統設定沿用同一儲存/管理機制(此為設計意圖,本 feature 只暴露單一-session 一個設定)。
- **沿用授權系統**:授權沿用既有角色/權限機制,最高權限角色(對齊既有其他管理介面的 Super-only 慣例)掌管這些控制。
- **沿用操作稽核**:設定/policy 變更稽核沿用既有操作稽核紀錄(操作者歸因)。
- **新增管理頁需治理 amendment**:新增一個管理員設定頁屬既有「受管 base-web 例外軌道」之外的新前端面 —— 預期需一條治理 amendment(於規劃階段處理)。
- **單實例為主**:現行部署為單實例;設定值跨多實例一致性為正交的設計屬性,多實例調校不在本 feature 重點。
- **「每裝置一個 session」OUT**:沿 028 FR-013,仍不在本 feature。
