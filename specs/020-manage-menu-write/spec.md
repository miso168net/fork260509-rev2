**Feature Branch**: `020-manage-menu-write`

**Created**: 2026-06-02

**Status**: Draft

**Input**: User description: "Phase 4 主流業務 — menu 寫端 CRUD:把 019 唯讀選單管理頁閉成完整 CRUD。新增/編輯/刪除選單,寫入 019 建的選單資料表(sys_menu);因 runtime 導覽(getUserRoutes)與管理頁共讀同源,寫端變更即時反映於導覽(D1 統一源 payoff)。可見性仍走既有 Casbin 權限把關(不在本波編輯)。凍結設計來源:[`docs/superpowers/020-manage-menu-write.md`](../../docs/superpowers/020-manage-menu-write.md)(Phase 0 brainstorm,D1–D5 user 親決)"

## Clarifications

### Session 2026-06-02 (Phase 0 brainstorm 親決 D1–D5)

- Q: 020 寫端範圍? → A: **menu 定義 CRUD(4 端點)**(D1):新增/編輯/刪除/批次刪除選單,寫 019 的選單資料表。「角色×選單可見性」編輯(MenuAuth,在角色管理頁、動既有 Casbin 可見性 policy)**不在本波**,為獨立後續 feature。
- Q: 編輯選單時哪些欄不可改? → A: **路由名(routeName)與選單類型(menuType)editable 時 immutable**(D2):routeName 是穩定鍵(對齊既有 Casbin 可見性 policy 鍵 + runtime 導覽的選單識別碼),可改會讓既有可見性把關對不上;menuType 建立後固定。其餘定義欄可改。
- Q: 寫端要不要動到既有可見性把關? → A: **不動**(D3):本波 runtime 完全不改既有 Casbin 可見性 policy,亦不為新選單自動賦予可見性。新選單在可見性被指派(後續 MenuAuth feature)前,顯示於管理頁、但不出現在 runtime 導覽。職責切分乾淨(對齊 019 的「定義」與「可見性」分離)。
- Q: 系統內建選單要不要保護? → A: **6 筆種子選單保護不可刪/不可停用**(D4):對應現有導覽骨幹的內建選單受保護(避免刪掉選單管理頁本身造成自鎖);其餘定義欄(名稱/圖示/排序等)仍可編輯。
- Q: 刪除有子選單的父怎麼處理? → A: **擋下**(D5):刪除具「有效子選單」的父選單一律被拒(提示先刪子選單),不連帶刪、不留孤兒;批次刪除中任一筆命中種子或具子選單 → 整批拒、不做部分執行。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 維運者新增選單(含子選單)(Priority: P1)

身為系統維運者(最高權限),我希望在「選單管理」頁新增選單(頂層或某選單之下的子選單),把新的導覽項目納入系統的選單定義單一真相。

**Why this priority**: 「新增」是把選單管理頁從唯讀變成可寫的第一步,也是「DB-driven 統一源」可被擴充的前提。可單獨交付(新增選單並於管理頁顯示)即構成價值。

**Independent Test**: 以最高權限身分新增一筆選單(填類型/名稱/路由名/路徑/圖示/排序/狀態/按鈕等)→ 管理頁列表出現該筆真實資料;以重複路由名新增 → 被拒(業務錯誤)。

**Acceptance Scenarios**:

1. **Given** 一個最高權限維運者, **When** 新增一筆頂層選單(含選單定義欄與按鈕集合), **Then** 該選單持久化於選單資料表並出現在管理頁列表,識別碼為字串。
2. **Given** 同一維運者選定某目錄型選單, **When** 在其下新增子選單, **Then** 新選單以該目錄為上層父選單建立(父子關係正確)。
3. **Given** 系統已有某路由名的有效選單, **When** 以相同路由名新增, **Then** 被拒並回業務錯誤(路由名在有效集內須唯一)。
4. **Given** 剛新增、尚未被指派可見性的選單, **When** 任一角色取得 runtime 導覽, **Then** 該選單不出現在導覽(可見性未指派);但維運者於管理頁仍看得到它。

### User Story 2 - 維運者編輯選單(穩定鍵不可改)(Priority: P1)

身為系統維運者,我希望編輯既有選單的定義(名稱、路徑、圖示、排序、狀態、旗標、按鈕等),且因 runtime 導覽與管理頁共讀同源,編輯**即時反映**於導覽(對已可見的選單)。

**Why this priority**: 「編輯即時反映於導覽」是「DB-driven 統一源(D1)」最直接的價值證明 —— 沒有它,DB-driven 只是換了儲存位置。可單獨驗證(編輯既有可見選單→導覽更新)。

**Independent Test**: 編輯一個既有且可見的選單(如改其排序或顯示標題)→ runtime 導覽即時反映新值,其餘選單維持不變;嘗試改其路由名/選單類型 → 不生效(被忽略)。

**Acceptance Scenarios**:

1. **Given** 一個既有且對某角色可見的選單, **When** 維運者編輯其定義欄(如排序或標題)並儲存, **Then** 該角色的 runtime 導覽即時反映新值,且其餘選單輸出維持不變。
2. **Given** 編輯模式, **When** 維運者嘗試變更路由名(routeName)或選單類型(menuType), **Then** 該兩欄不被變更(穩定鍵,送出亦忽略),其餘欄正常更新。
3. **Given** 一個不存在或已刪除的選單, **When** 嘗試編輯, **Then** 被拒並回業務錯誤(選單不存在)。
4. **Given** 任一選單的更新, **When** 更新成功, **Then** 寫入更新時間與操作者(稽核中介資料)成對記錄。

### User Story 3 - 維運者刪除選單(種子保護 + 父子守則)(Priority: P1)

身為系統維運者,我希望刪除不再需要的選單(單筆或批次),且系統會擋下會造成傷害的刪除(刪到系統內建骨幹、或刪掉仍有子選單的父)。

**Why this priority**: 「刪除」閉合完整 CRUD;保護機制避免維運者誤刪導致自鎖或孤兒,是可安全交付的前提。可單獨驗證(刪除自訂選單成功、刪種子/具子被拒)。

**Independent Test**: 刪除一筆自訂葉選單 → 軟刪後不再出現於列表;刪除種子選單 → 被拒;刪除仍有有效子選單的父 → 被拒(提示先刪子);批次含種子或具子 → 整批拒。

**Acceptance Scenarios**:

1. **Given** 一筆自訂的有效葉選單, **When** 維運者刪除它, **Then** 該選單被可復原軟刪除、不再出現於列表,且記錄刪除時間與操作者。
2. **Given** 一筆系統內建種子選單, **When** 嘗試刪除或停用, **Then** 被拒並回業務錯誤(不可刪除/停用系統內建選單)。
3. **Given** 一個仍有有效子選單的父選單, **When** 嘗試刪除, **Then** 被拒並回業務錯誤(請先刪除子選單)。
4. **Given** 一批要刪除的選單,其中含種子選單或具子選單者, **When** 執行批次刪除, **Then** 整批被拒、不做部分執行(無任一筆被刪)。

### Edge Cases

- **路由名重複**:於有效集內以已存在的路由名新增 → 被拒(業務錯誤);軟刪後的同名路由名可重用(有效集唯一)。
- **種子保護**:6 筆系統內建選單(對應現有導覽骨幹)刪除或停用 → 一律被拒;其餘定義欄(名稱/圖示/排序等)仍可編輯。
- **父子守則**:刪除具有效子選單的父 → 被拒(不連帶刪、不留孤兒);種子父選單同時受種子保護。
- **批次原子性**:批次刪除中任一筆命中種子或具子 → 整批拒、0 部分執行。
- **新選單可見性**:新增選單未指派可見性前 → 顯示於管理頁、不出現於 runtime 導覽(可見性由後續 MenuAuth feature 指派);本波寫端不自動賦予可見性。
- **編輯穩定鍵**:嘗試改 routeName/menuType → 忽略(不生效),其餘欄正常更新。
- **不存在/已軟刪**:編輯或刪除不存在/已軟刪選單 → 業務錯誤(不存在),非基建錯誤。
- **回歸**:本波寫端 MUST NOT 破壞 019 三讀端、getUserRoutes 既有(未編輯時)逐字輸出、既有授權把關、既有 user/role 寫端(以回歸測試覆蓋)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供選單的新增、編輯、刪除(單筆與批次)寫入能力,寫入既有選單資料表(019 sys_menu,選單定義單一真相);因 runtime 導覽與管理頁共讀同源,寫端對「已可見選單」的變更 MUST 即時反映於 runtime 導覽(D1 payoff)。
- **FR-002**: 新增選單 MUST 支援頂層與子選單(由上層父選單決定父子關係);選單路由名(routeName)在有效(未軟刪)集內 MUST 唯一,重複 MUST 回業務錯誤。
- **FR-003**: 編輯選單 MUST NOT 變更路由名(routeName,穩定鍵)與選單類型(menuType);其餘定義欄(名稱/路徑/目標頁/圖示/圖示類型/排序/啟用狀態/路由旗標/按鈕集合/query 等)MUST 可更新。
- **FR-004**: 刪除選單 MUST 為可復原軟刪除(沿既有業務表慣例),單筆與批次皆 MUST 支援;刪除與更新 MUST 成對寫入稽核中介資料(操作者 + 時間,對齊 §I.6)。
- **FR-005**: 系統內建種子選單(對應現有導覽骨幹的選單)MUST 受保護:不可刪除、不可停用;其餘定義欄 MUST 仍可編輯。
- **FR-006**: 刪除具有效子選單的父選單 MUST 被拒(回業務錯誤、提示先刪子選單),不連帶刪、不留孤兒;批次刪除中任一筆命中種子或具子選單 → MUST 整批拒、不做部分執行。
- **FR-007**: 選單寫端 MUST 限最高權限管理員(Super)存取;其他已認證使用者 MUST 被拒(權限不足),未認證請求 MUST 被拒(沿既有授權把關與錯誤碼)。
- **FR-008**: 選單可見性(哪角色看哪選單)MUST 維持由既有 Casbin 權限把關決定(§I.2);本波寫端 MUST NOT 改動既有可見性 policy 資料,亦 MUST NOT 為新選單自動賦予可見性 → 新選單在可見性被指派(後續 feature)前不出現於 runtime 導覽,但出現於管理頁。
- **FR-009**: 業務驗證錯誤(路由名重複 / 種子保護 / 具子選單 / 選單不存在 / 非法輸入)MUST 以既有「業務錯誤」碼回應(非授權/基建類);回傳沿既有統一回應格式與字串識別碼契約。
- **FR-010**: 每筆選單的按鈕集合(按鈕代碼 + 說明)MUST 能隨選單新增/編輯一併寫入(承 019 結構化集合欄);此為選單定義,MUST NOT 與既有「角色可用按鈕代碼」權限矩陣混為一談(本波不動該矩陣)。
- **FR-011**: 本波 MUST NOT 包含角色—選單可見性編輯入口(MenuAuth/ButtonAuth)、選單復原(restore 軟刪選單)、以及變更既有選單的上層父選單(re-parent),皆留後續 feature。
  > **supersede**:選單復原(restore)與 re-parent(變更上層父選單)原列本波 OUT,已於 025-menu-restore-reparent(merge `6225bd8`)補完。
- **FR-012**: 既有能力 MUST NOT 因寫端落地而被破壞(回歸):019 三讀端(選單列表/樹/頁面選項)、getUserRoutes 既有(未編輯時)逐字輸出與常數路由、既有授權把關(login/enforce)、既有 user/role 寫端與清單顯示皆維持原行為。

### Key Entities *(include if data involved)*

- **選單(Menu)**:承 019 的選單資料表(sys_menu)—— 類型 / 名稱 / 路由名(穩定鍵)/ 路徑 / 目標頁 / 圖示(及類型)/ 排序 / 啟用狀態 / 上層父選單 / 按鈕集合(代碼+說明)/ 路由行為旗標 / 稽核中介資料。本波新增「寫入路徑」(新增 / 編輯 / 軟刪 + §I.6 成對稽核),不新增欄位。
- **種子選單(Seed menus)**:對應現有導覽骨幹的系統內建選單(首頁 + 管理及其子項);受保護:不可刪除/停用,可編輯其餘定義欄。
- **選單可見性授權(Menu visibility)**:既有的「角色 × 選單」可見性把關(由既有 Casbin 權限機制提供);本波只**讀用**、MUST NOT 改其資料或機制,亦不為新選單自動賦予可見性。

## Success Criteria *(mandatory)*

> 下列百分比指對所列舉的代表性 case 矩陣**全數通過**(各類正反例至少各一),非統計抽樣。

### Measurable Outcomes

- **SC-001**: 最高權限維運者可於選單管理頁完整新增 / 編輯 / 刪除選單,變更 100% 持久化於選單資料表並反映於管理頁列表(取代先前未接線的寫操作)。
- **SC-002**: 編輯既有且可見的選單後,runtime 導覽 100% 即時反映該變更(證 DB-driven 統一源);**未被編輯的選單其 runtime 導覽輸出維持與本波前一致**(延續 019 逐字基線)。
- **SC-003**: 路由名(routeName)與選單類型(menuType)100% 不可於編輯變更(送出亦被忽略);有效集內路由名重複 100% 被拒。
- **SC-004**: 種子選單 100% 不可刪除/停用;具有效子選單的父 100% 不可直接刪除;批次含此類者 100% 整批拒、0% 部分執行。
- **SC-005**: 選單寫端授權把關正確:最高權限者(Super)寫入成功率 100%,其他已認證使用者與未認證請求被拒比例 100%(0% 越權寫入)。
- **SC-006**: 本波寫端 100% 不改動既有可見性 policy 資料;新增選單於可見性被指派前 0% 出現於 runtime 導覽、100% 出現於管理頁。
- **SC-007**: 刪除 100% 為可復原軟刪除,且更新/刪除 100% 成對寫入稽核中介資料(操作者 + 時間)。
- **SC-008**: 既有能力於本波改動後 100% 不被破壞(回歸):019 三讀端 / getUserRoutes 既有逐字輸出與常數路由 / 既有授權把關 / 既有 user/role 寫端與清單顯示。

## Assumptions

- **範圍 = menu 定義 CRUD(D1)**:4 個寫端點(新增/編輯/刪除/批次刪除)寫 019 的選單資料表;角色—選單可見性編輯(MenuAuth)留獨立後續 feature。
- **穩定鍵 immutable(D2)**:routeName 對齊既有可見性 policy 鍵與 runtime 導覽識別碼,編輯不可改;menuType 建立後固定。
- **不動可見性把關(D3)**:本波 runtime 不改既有 Casbin 可見性 policy、不自動賦予新選單可見性;新選單可見性由後續 feature 指派。
- **種子保護(D4)**:對應現有導覽骨幹的 6 筆內建選單不可刪/停用、可編輯其餘欄。
- **父子守則(D5)**:刪除具有效子選單的父被拒;批次含種子或具子整批拒。
- **沿用既有能力**:沿用既有選單資料表(019,**不建表/不加欄**)、軟刪除模型與過濾邊界、稽核成對寫入機制(§I.6,操作者由既有請求情境提供)、統一回應格式與業務錯誤碼、對外字串識別碼契約、授權把關(Super-only,沿 017/018 寫端);選單上的按鈕集合以既有結構化欄承載(承 019)。
- **前端沿用既有選單管理頁**:既有新增/編輯/刪除控制項(目前未接線)於本波接上既有受管接線軌道,不改 form 結構/型別。
- **跨既有能力的觸及與回歸範圍**:本波對 019 選單資料表加寫入路徑,屬對既有讀端能力(019)的擴充 —— MUST 以回歸驗證既有讀端、getUserRoutes 既有逐字輸出、授權把關不被破壞(見 SC-008);wire 形狀對齊與前端送出形的細節於規劃/研究階段以實際 code 與既有契約對齊(plan/research)。
