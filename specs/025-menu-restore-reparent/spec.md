## User Scenarios & Testing *(mandatory)*

### User Story 1 - 維運者復原誤刪的選單 (Priority: P1)

身為系統維運者,我希望把一個**誤刪(軟刪除)的選單**從「已刪除」清單復原回使用狀態,而不必直接動資料庫救援。

**Why this priority**: 這是資料遺失的安全網 —— 目前刪錯選單後沒有任何介面能復原,只能下原始 SQL。單獨交付即構成價值(誤刪可救),是 MVP。

**Independent Test**: 刪除一個自訂選單 → 切到「已刪除」檢視看到它 → 按「復原」→ 該選單回到選單列表與導覽、可正常使用;復原動作記錄操作者與時間。

**Acceptance Scenarios**:

1. **Given** 一筆被軟刪除、且其上層父選單仍存在的選單, **When** 維運者於已刪除清單按復原, **Then** 該選單回到使用狀態、重新出現於選單列表與受影響使用者的導覽,並寫入復原稽核(操作者 + 時間)。
2. **Given** 一筆被軟刪除、但其**上層父選單也已被刪除**的選單, **When** 維運者嘗試復原它, **Then** 系統拒絕並提示「上層選單已刪除,請先復原上層」,該選單維持已刪除狀態。
3. **Given** 一筆被軟刪除的選單,其穩定識別(路由名)在刪除後已被另一筆**使用中**選單佔用, **When** 維運者嘗試復原它, **Then** 系統拒絕並提示路由名已被占用,避免識別衝突。

---

### User Story 2 - 維運者重組選單階層(搬移上層) (Priority: P2)

身為系統維運者,我希望把一個**自訂**選單搬到不同的上層父選單之下(或搬成頂層),而不必刪掉重建(刪掉重建會丟失該選單的識別、稽核歷史與既有可見性授權)。

**Why this priority**: 重組導覽結構的真實需求;與 US1 同屬選單管理收尾,但屬便利性而非資料安全,故次要。

**Independent Test**: 編輯一筆自訂選單、改其上層為另一個目錄選單(或頂層)→ 儲存 → 該選單即時出現在新位置的導覽下,路由名與既有可見性授權維持不變。

**Acceptance Scenarios**:

1. **Given** 一筆自訂選單與一個有效的目錄選單, **When** 維運者於編輯介面把它的上層改為該目錄並儲存, **Then** 該選單即時(無需重啟)出現在新上層之下、原位置不再有它;其路由名與可見性授權不變。
2. **Given** 一筆自訂選單, **When** 維運者嘗試把它搬到**它自己或其子孫**之下, **Then** 系統拒絕(不可形成循環),階層維持原狀。
3. **Given** 一筆**系統內建(種子)**選單, **When** 維運者嘗試變更其上層, **Then** 系統拒絕並提示不可移動系統內建選單,其上層維持固定。
4. **Given** 一個無效的目標上層(非目錄選單、或不存在/已刪除的選單), **When** 維運者嘗試把選單搬到其下, **Then** 系統拒絕並提示上層無效。

---

### User Story 3 - 既有選單管理不被破壞 + 即時反映 (Priority: P3)

身為系統維運者,我希望復原與搬移**即時反映於導覽**,且既有的選單管理行為(新增/編輯/刪除/批次刪/種子保護/穩定識別與類型不可改/選單可見性與按鈕權限編輯)不因本波被破壞。

**Why this priority**: 一致性與正確性保障(安全網),優先序最低但必要。

**Independent Test**: 復原/搬移後立即檢視受影響角色的導覽即時反映新狀態;逐項驗證既有選單管理行為與本波前一致。

**Acceptance Scenarios**:

1. **Given** 一筆選單被復原或搬移上層, **When** 變更完成, **Then** 受影響使用者的導覽即時反映新狀態(無需重啟、無陳舊顯示)。
2. **Given** 既有的選單管理能力, **When** 本波交付後, **Then** 新增/編輯/刪除/批次刪、種子選單不可刪、路由名與選單類型不可改、選單可見性與按鈕權限編輯,皆維持原行為。

### Edge Cases

- **復原父已刪**:子選單復原時其父已被刪 → 擋下、要求先復原上層(不自動升頂層、不產生看不見的選單)。
- **復原識別衝突**:刪除後路由名被新的使用中選單佔用 → 復原被擋。
- **復原非已刪/不存在目標**:對一筆本就使用中或不存在的選單按復原 → 回「選單不存在或未刪除」、不誤動。
- **搬移形成循環**:把選單搬到自己或其子孫之下 → 擋(防止樹結構損壞)。
- **搬移系統內建選單**:種子選單上層固定 → 擋。
- **搬移到無效上層**:目標非目錄、或目標已刪/不存在 → 擋。
- **級聯**:復原父不自動復原其已刪子(逐筆復原、由上而下);刪父前其本無使用中子(既有刪除守則),故復原順序為先父後子。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓維運者**檢視已軟刪除的選單清單**(與使用中選單清單區隔)。
- **FR-002**: 系統 MUST 讓維運者**復原**一筆已軟刪除的選單回到使用狀態,並**成對寫入稽核中介資料**(復原的操作者 + 時間,對齊既有業務表慣例)。
- **FR-003**: 復原 MUST 僅在該選單的**上層父選單仍存在(未刪除)**時允許;父已刪除 → 拒絕並提示先復原上層(頂層選單無此限制)。
- **FR-004**: 復原 MUST 僅在該選單的**穩定識別(路由名)未被其他使用中選單佔用**時允許;已被佔用 → 拒絕。
- **FR-005**: 系統 MUST 讓維運者**變更一筆自訂選單的上層父選單**(含搬為頂層),變更 MUST 即時反映於導覽(無需重啟、跨服務實例一致)。
- **FR-006**: 變更上層 MUST NOT 允許形成**循環**(把選單搬到它自己或其子孫之下)→ 拒絕、階層不變。
- **FR-007**: 變更上層的目標 MUST 僅允許**有效的目錄選單或頂層**;目標非目錄、或不存在/已刪除 → 拒絕。
- **FR-008**: **系統內建(種子)選單的上層 MUST NOT 可被變更**(維持 canonical 導覽結構,與「種子選單不可刪除」一致);僅自訂選單可重組。
- **FR-009**: 復原與搬移 MUST 即時反映於受影響使用者的導覽(無陳舊顯示),沿用既有選單可見性/導覽機制。
- **FR-010**: 既有能力 MUST NOT 因本波被破壞(回歸):選單新增/編輯/刪除/批次刪除、種子選單不可刪除、穩定識別(路由名)與選單類型不可變更、選單可見性與按鈕權限編輯,皆 MUST 維持原行為。
- **FR-011**: 復原與搬移 MUST 為**僅限最高權限(維運者)**之操作;其餘角色不得執行。

### Key Entities *(include if data involved)*

- **選單(Menu)**:導覽項目,具「使用中 / 已軟刪除」兩態、以**上層父選單**形成樹狀階層、以**穩定識別(路由名)**為鍵(對齊既有可見性授權)。本波擴增「復原」與「變更上層(限自訂)」兩種狀態轉移。
- **已刪除選單集合(Recycle)**:已軟刪除、可復原的選單集合;作為復原操作的來源清單。

## Success Criteria *(mandatory)*

> 下列百分比指對所列舉的代表性 case 矩陣**全數通過**(各類正反例至少各一),非統計抽樣。

### Measurable Outcomes

- **SC-001**: 維運者可經介面復原一筆誤刪選單,變更 100% 回到使用狀態並即時反映於導覽,且 100% 寫入復原稽核(操作者 + 時間),**無需動資料庫**。
- **SC-002**: 復原防護 100% 正確擋下不合法復原(上層已刪、路由名已被佔用、目標非已刪),且 0 誤動既有資料。
- **SC-003**: 維運者可變更自訂選單的上層,變更 100% **即時反映於導覽**(獲影響角色立即見新位置),無需重啟。
- **SC-004**: 不合法搬移 100% 被擋(循環、系統內建選單、無效上層),且 0 破壞既有階層。
- **SC-005**: 回歸:既有選單管理行為(新增/編輯/刪除/批次刪/種子保護/識別與類型不可改/可見性與按鈕權限編輯)100% 維持原行為。
- **SC-006**: 本波對授權與選單階層資料的變更 100% 可逆還原,且 0 影響既有選單可見性與按鈕授權。

## Assumptions

- **沿用既有軟刪除、稽核、選單可見性機制**:本波只補「復原」與「自訂選單變更上層」兩種狀態轉移,**不新增資料表、不改可見性機制本身、不改穩定識別與類型不可變更的既有規則**。
- **復原為逐筆、非級聯**:復原父選單不自動復原其已刪子;復原順序為由上而下(先復原父、再復原子)。
- **種子選單上層固定**:僅自訂選單可重組階層(R2 親決);種子選單仍可編輯名稱等定義欄(沿既有)。
- **回收桶 = 選單頁的「顯示已刪除」檢視切換**(R3 親決),非獨立頁面、非彈窗。
- **wire 形狀與操作沿既有選單管理契約**;本波不在 spec 固定路由名/識別字串的確切命名(規劃/研究階段以實際 code 對齊)。
