# Feature Specification: Menu Management List (DB-driven menu source)

**Feature Branch**: `019-manage-menu-list`

**Created**: 2026-06-02

**Status**: Draft

**Input**: User description: "Phase 4 主流業務 — menu 改 DB-driven:建立 menu 業務資料表為選單定義的單一真相,讓 runtime 導覽選單(getUserRoutes)與選單管理頁(getMenuList/getMenuTree/getAllPages)共讀同一來源,可見性仍走既有 Casbin 權限把關。本波只做讀端 + runtime 來源遷移(寫端 CRUD 留下一波)。凍結設計來源:[`docs/superpowers/019-manage-menu-list.md`](../../docs/superpowers/019-manage-menu-list.md)(Phase 0 brainstorm,D1–D5 user 親決)"

## Clarifications

### Session 2026-06-02 (Phase 0 brainstorm 親決 D1–D5)

- Q: 選單的資料來源? → A: **DB-driven 統一源**(D1):新增選單業務資料表(menu store)作為選單定義的單一真相;runtime 導覽選單與選單管理頁**共讀同一來源**。對齊「base-web 為權威」—— 日後編輯選單會真實反映於導覽。
- Q: 本波範圍? → A: **讀端 + runtime 來源遷移**(D2):本波建表 + 把 runtime 導覽選單改由資料表供應 + 選單管理頁三個讀取端點;選單的新增/編輯/刪除(寫端)留下一波(020)。
- Q: 選單上的按鈕(buttons)如何儲存? → A: 以選單記錄內的**結構化集合欄位**儲存(D3,每筆 = 按鈕代碼 + 說明)。此為「某選單有哪些按鈕」的定義,與既有「角色可用哪些按鈕代碼」的權限矩陣(013 getUserInfo)是兩件事 —— 本波不動該權限矩陣。
- Q: 選單可見性(哪個角色看哪個選單)由誰決定? → A: **維持既有 Casbin 權限把關不變**(D4,§I.2 NON-NEGOTIABLE):資料表存「選單定義」,既有 menu 可見性 policy 存「哪角色看哪選單」。角色—選單可見性的**編輯**(角色編輯頁的選單授權彈窗)**不在本波**,留後續受管 policy / menu-auth feature。
- Q: runtime 導覽選單遷到資料表後,對前端的影響? → A: **輸出必須逐字不變**(D5,回歸鐵律):runtime 導覽選單在改由資料表供應後,各角色看到的選單階梯與遷移前**完全一致**;常數路由(登入/404/403 等前端專屬路由)維持前端供應、不入資料表、不變。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - runtime 導覽選單改由資料表供應(DB-driven 來源,輸出不變)(Priority: P1)

身為任何已登入使用者,我在登入後看到的左側導覽選單,其定義改由後端的選單資料表供應(而非寫死於程式碼);但我實際看到的選單項目與權限階梯**與改動前完全一致**。

**Why this priority**: 這是「DB-driven 統一源」的地基 —— 沒有它,選單管理頁的編輯(下一波)就無從反映於真實導覽。它同時是本波最高風險(動到已上線的 runtime 導覽),故須以「輸出逐字不變」為驗收核心。可單獨交付(來源遷移、行為不變)即構成「選單來源統一」的價值。

**Independent Test**: 以三種角色(最高權限 / 一般管理 / 一般使用者)分別登入,取得各自的導覽選單,逐一比對遷移前後的選單樹(項目、層級、順序、各欄位)**完全相同**;停用某角色仍即時影響其導覽可見性(沿既有把關)。

**Acceptance Scenarios**:

1. **Given** 一個最高權限使用者, **When** 取得其導覽選單, **Then** 回傳的選單樹(含父子層級、首頁項、各選單的標題/路由/圖示等)與遷移前**逐字一致**。
2. **Given** 三種不同權限的使用者, **When** 各自取得導覽選單, **Then** 各角色看到的選單階梯維持原樣(高權限看到的最多、一般使用者最少),且可見性仍由既有權限把關決定。
3. **Given** 前端啟動所需的常數路由(登入/404/403 等), **When** 取得常數路由, **Then** 其內容與遷移前完全相同(常數路由不入資料表、不受本波影響)。
4. **Given** 一個無任何有效角色的使用者, **When** 取得導覽選單, **Then** 不回傳任何需授權的選單(沿既有把關,不崩潰)。

---

### User Story 2 - 選單管理頁顯示真實選單結構(讀端)(Priority: P1)

身為系統維運者,我希望在「選單管理」頁看到系統真實的選單結構(分頁列表、父子樹、可用頁面選項),以便檢視目前的選單配置(編輯能力於下一波提供)。

**Why this priority**: 把選單管理頁從「打 mock / 空白」變成顯示真實資料,是本波對維運者的可見價值,且與 US1 共用同一份選單資料表(同源)。可單獨驗證(管理頁讀取三端點顯示真值)。

**Independent Test**: 以具權限的維運者身分開啟選單管理頁 → 列表顯示資料表內的選單(分頁)、樹狀檢視顯示父子關係、頁面選項下拉顯示可用頁面集;非授權身分讀取被拒。

**Acceptance Scenarios**:

1. **Given** 一個具選單管理讀取權限的維運者, **When** 取得選單列表, **Then** 回傳資料表內的選單(分頁結構),每筆含選單定義欄位(類型/名稱/路由/圖示/排序/狀態/按鈕等),識別碼為字串。
2. **Given** 同一維運者, **When** 取得選單樹, **Then** 回傳父子巢狀結構供「上層選單」選擇用。
3. **Given** 同一維運者, **When** 取得可用頁面選項, **Then** 回傳可指派為選單目標的頁面集合。
4. **Given** 一個非授權身分(或未認證請求), **When** 嘗試讀取選單管理端點, **Then** 被拒(權限不足 / 未認證)。

---

### Edge Cases

- **選單樹孤節點 / 父不存在**:某選單的上層指向不存在或已軟刪的父 → 樹組裝時略過該掛接、不崩潰(以可顯示的根節點為準)。
- **選單可見性與定義分離**:選單定義存在於資料表、但某角色無對應可見性授權 → runtime 導覽對該角色不顯示該選單(定義在、可見性無);管理頁(具管理權限者)仍可看到該選單定義。
- **常數路由**:登入/404/403/500/iframe 等前端專屬路由不屬業務選單 → 不入資料表、不出現在選單管理列表、由前端常數路由供應。
- **無有效角色**:使用者所有角色停用/軟刪 → runtime 導覽不回需授權選單(沿既有有效角色把關)。
- **空選單表(理論)**:若資料表無任何有效選單 → runtime 導覽只回首頁項(或空),不崩潰。
- **回歸:既有權限把關**:本波改 runtime 選單來源 MUST NOT 破壞既有授權把關、既有 user/role 寫端、既有清單顯示(以回歸測試覆蓋)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 以一個持久化的**選單資料表**作為選單定義的單一真相;runtime 導覽選單與選單管理頁 MUST 讀取同一來源(不再有「程式碼內常數」與「管理頁資料」兩套分歧來源)。
- **FR-002**: runtime 導覽選單(登入後取得的選單樹)MUST 由選單資料表供應;且其對外輸出 MUST 與來源遷移前**逐字一致**(各角色看到的選單項目、父子層級、順序、各欄位皆不變)。
- **FR-003**: 選單可見性(哪個角色看到哪個選單)MUST 維持由既有 Casbin 權限把關決定(§I.2),不改判定機制;停用/軟刪角色對選單可見性的即時效果沿既有(承 018)。本波 MUST NOT 改動既有 menu 可見性 policy 資料。
- **FR-004**: 系統 MUST 提供選單管理頁所需的三個讀取端點:選單列表(分頁)、選單樹(父子巢狀)、可用頁面選項;回傳對齊既有前端契約。
- **FR-005**: 常數路由(前端啟動所需的登入/404/403/500/iframe 等)MUST 維持由前端常數路由供應、MUST NOT 納入選單資料表、且其供應行為本波不變。
- **FR-006**: 選單資料表 MUST 含建立/更新/刪除的時間與操作者稽核欄(對齊 §I.6 業務主表審計欄標準),且為可復原的軟刪除模型(沿既有業務表慣例);本表為審計欄標準凍結後新建,於建表當下即備齊審計欄。
- **FR-007**: 對外輸出的識別碼 MUST 維持**字串**形式;選單上的列舉欄(選單類型、圖示類型、啟用狀態)對外以既有契約的字串列舉表示;回傳沿既有統一回應格式。
- **FR-008**: 每筆選單 MUST 能承載其按鈕集合(按鈕代碼 + 說明)作為選單定義的一部分,於選單管理列表回傳;此為選單定義,MUST NOT 與既有「角色可用按鈕代碼」權限矩陣混為一談(本波不改該矩陣)。
- **FR-009**: 選單管理讀取端點 MUST 限具相應權限者存取;未授權 / 未認證請求 MUST 被拒(沿既有授權把關與錯誤碼)。
- **FR-010**: 本波 MUST NOT 包含選單的新增/編輯/刪除(寫端),亦 MUST NOT 包含角色—選單可見性的編輯入口(留後續 feature);選單管理頁既有的寫端控制項本波維持未接線。

### Key Entities *(include if feature involves data)*

- **選單(Menu)**:一個導覽選單項目 —— 類型(目錄 / 葉選單)、名稱、路由名(建立後固定的穩定鍵,對應可見性把關)、路由路徑、目標頁面、圖示(及圖示類型)、排序、啟用狀態、上層選單(父子樹關係)、以及一組按鈕定義(代碼 + 說明)與路由行為旗標(是否隱藏於選單、是否快取、是否常數、外連結等);另含建立/更新/刪除的時間與操作者(稽核中介資料)。系統初始選單(對應現有導覽:首頁 + 管理及其子項)為種子資料。
- **選單可見性授權(Menu visibility)**:既有的「角色 × 選單」可見性把關(由既有權限機制提供);本波只**讀用**之過濾 runtime 導覽,不改其資料或機制。
- **常數路由(Constant routes)**:前端啟動所需、與業務選單無關的固定路由(登入/404/403 等);不屬選單資料表、由前端供應。

## Success Criteria *(mandatory)*

> 下列百分比指對所列舉的代表性 case 矩陣**全數通過**(各類正反例至少各一),非統計抽樣。

### Measurable Outcomes

- **SC-001**: runtime 導覽選單改由資料表供應後,三種角色(最高權限 / 一般管理 / 一般使用者)各自的選單樹與遷移前**100% 逐字一致**(0% 項目/層級/順序/欄位差異)。
- **SC-002**: 選單管理頁能顯示資料表內的真實選單(列表分頁 + 父子樹 + 頁面選項),取代先前的 mock / 空白。
- **SC-003**: 選單可見性把關 100% 維持:停用/軟刪角色對其 runtime 導覽的影響沿既有即時生效;無有效角色者不獲任何需授權選單(0% 越權顯示)。
- **SC-004**: 常數路由供應 100% 不變(與遷移前逐字一致)。
- **SC-005**: 選單管理讀取端點之授權把關正確:具權限者讀取成功率 100%,未授權 / 未認證請求被拒比例 100%。
- **SC-006**: 對外識別碼 100% 維持字串形式;選單列舉欄對外以既有契約字串列舉表示。
- **SC-007**: 選單資料表於建表當下即具備完整審計欄(建立/更新/刪除的時間與操作者),且為可復原軟刪除模型(審計欄標準凍結後新建表 0% 留 retrofit 債)。
- **SC-008**: 既有能力於本波改動(runtime 選單來源遷移)後 100% 不被破壞(回歸):既有授權把關(login/enforce)、既有 user/role 寫端、既有清單顯示、既有常數路由與動態路由其餘端點皆維持原行為。

## Assumptions

- **DB-driven 統一源**(D1):選單定義移至選單資料表作為單一真相;runtime 導覽與管理頁共讀之。對齊「base-web 為權威」—— 管理頁編輯(下一波)將真實反映於導覽。
- **本波範圍 = 讀端 + runtime 遷移**(D2):建表 + runtime 導覽改讀資料表 + 三讀取端點;選單寫端 CRUD 留 020。
- **可見性沿既有 Casbin 把關不變**(D4,§I.2):資料表存定義、既有可見性 policy 存「哪角色看哪選單」;選單路由名為穩定鍵、對齊既有可見性 policy 鍵。角色—選單可見性編輯入口留後續。
- **輸出逐字不變**(D5):runtime 導覽遷源後對前端透明;種子選單須精準重現現有程式碼內導覽樹,以達成「逐字一致」。
- **按鈕為選單定義的一部分**(D3):以選單記錄內結構化集合儲存;與既有角色—按鈕權限矩陣(013)分離、本波不動該矩陣。
- **常數路由前端供應**:登入/404/403 等不入資料表、本波不變。
- **沿用既有能力**:沿用既有統一回應格式與錯誤碼、授權把關、軟刪除過濾邊界、稽核寫入機制、既有資料存取慣例、對外字串識別碼契約;前端沿用既有選單管理頁(讀端控制項;若需新呼叫接點走既有受管 wrapper 軌道)。
- **跨既有能力的觸及與回歸範圍**:本波改 runtime 導覽選單的資料來源(由程式碼內常數改為資料表),屬對既有動態路由能力(014)的修訂 —— MUST 以回歸驗證既有授權與選單可見性行為不被破壞(見 SC-008);wire 形狀對齊與種子精準重現的細節於規劃/研究階段以實際 code 與 mock 對齊(plan/research)。
