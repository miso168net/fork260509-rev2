# Feature Specification: single-session enforcement(per-account 可控 + 系統預設)

**Feature Branch**: `028-single-session-enforcement`

**Created**: 2026-06-05

**Status**: Draft

**Input**: User description: "single-session enforcement — 把 027 刻意維持的『access stateless、多裝置並存』升級為 per-account 可控的 access 端單一-session:啟用的帳號一次只能一個有效登入、新登入即時踢舊;可逐帳號設定(繼承/開/關)+ 全站預設、028 預設關(dormant 上線);被取代 session 乾淨登出並提示『账号在他处登录』。**028 = 後端引擎 + policy 儲存**(base-web 零改、無新對外端點);管理 UI 拆 029。設計來源:[`docs/superpowers/028-single-session-enforcement.md`](../../docs/superpowers/028-single-session-enforcement.md)(Phase 0 brainstorm 全決)。"

> **性質**:這是一個**後端安全強化** feature —— 為「帳號共用 / 憑證外洩」提供遏制:啟用單一-session 的帳號,任何時刻只有最新一次登入有效,舊登入即時失效。**對未啟用的帳號零影響**(維持 027 多裝置並存);**028 全站預設『關』、dormant 上線**(既有使用者除一次性重新登入外無感)。價值在「可選的、可逐帳號控制的登入收斂」。**rust-api 單倉、base-web 零改**;啟用與否在 028 由後端設定,**管理介面(系統預設 runtime 可調 + 每帳號 UI 設定)拆為後續 feature 029**。下列 user story 兼採「安全姿態」與「使用者體驗」兩視角。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 啟用單一-session 的帳號,新登入即時使舊登入失效 (Priority: P1)

身為系統的安全守護者,我希望被標記為「單一-session」的帳號(例如高權限或共用風險帳號),**任何時刻只有最新一次登入有效**:當該帳號在另一處(另一瀏覽器/裝置)成功登入時,先前的登入要**立即失效**,其後續操作被登出。如此一來,帳號被共用或憑證被竊取後,攻擊者與真實使用者無法同時長期持有有效 session —— 後登入者取代先登入者。

**Why this priority**: 這是本 feature 的核心安全價值與存在理由。單獨交付即把「啟用帳號」從「可多處並存」收斂為「單一有效登入」,是 MVP。

**Independent Test**: 將某帳號設為單一-session;在 A 處登入並確認可正常操作;在 B 處以同帳號登入;回到 A 處發出任一受保護操作 → A 被登出、B 仍正常。

**Acceptance Scenarios**:

1. **Given** 一個已啟用單一-session 的帳號在 A 處登入且有效, **When** 同帳號在 B 處成功登入, **Then** A 處的下一個受保護操作被判定為失效並登出;B 處正常。
2. **Given** 啟用單一-session 的帳號剛在 B 處登入(成為當前有效 session), **When** A 處(舊 session)嘗試任一受保護操作, **Then** 回登出訊號、A 不再能操作。
3. **Given** 同帳號接連在 B、C 處登入, **When** 各處發出操作, **Then** 僅最後登入的 C 有效、A 與 B 皆已失效(任何時刻最多一個有效 session)。

### User Story 2 - 單一-session 可逐帳號設定,且有安全的全站預設 (Priority: P1)

身為系統操作者,我希望「是否啟用單一-session」**可逐帳號設定**(繼承系統預設 / 強制開 / 強制關),並有一個**全站預設**值;未啟用的帳號維持原本的多裝置並存。如此一來,我能只對需要的帳號收斂登入,而不強制所有使用者改變行為;且上線時以安全預設(關)滾動,不打擾既有使用者。

**Why this priority**: 與 US1 同列 P1 —— 沒有「可控 + 安全預設」,單一-session 會一刀切影響所有使用者、造成不可接受的行為回歸。可控性是讓 US1 可安全部署的必要配套。

**Independent Test**: 系統預設設為「關」,確認所有「繼承」帳號維持多裝置並存(US4);將單一帳號設為「開」,確認僅該帳號適用 US1、其他帳號不受影響。

**Acceptance Scenarios**:

1. **Given** 全站預設為「關」且某帳號 policy 為「繼承」, **When** 該帳號多處登入, **Then** 維持多裝置並存(不踢)。
2. **Given** 某帳號 policy 被設為「開」, **When** 該帳號多處登入, **Then** 適用 US1(新登入踢舊)。
3. **Given** 某帳號 policy 被設為「關」(覆寫系統預設), **When** 該帳號多處登入, **Then** 即使系統預設為開,該帳號仍維持多裝置並存。
4. **Given** 任一帳號的 policy 變更, **When** 另一不同帳號登入/操作, **Then** 不受影響(帳號間隔離)。

> 註(scope):028 的 policy 設定由**後端**進行(每帳號 policy + 系統預設);**圖形管理介面(系統預設 runtime 可調 + 使用者管理頁逐帳號設定)為後續 feature 029**。

### User Story 3 - 被取代的 session 乾淨登出並清楚告知,不卡死 (Priority: P2)

身為被「踢出」的使用者(例如我在新裝置登入後、舊裝置那邊),我希望舊裝置在下一個操作時**清楚告訴我「账号在他处登录」並乾淨地回到登入頁**,而不是無聲失敗、卡在錯誤迴圈、或不斷重試。如此一來,被收斂登入的體驗是可理解、不令人困惑的。

**Why this priority**: 直接決定 US1/US2 安全機制可不可用 —— 若被踢時陷入無限重試或卡死,即是不可接受的體驗回歸。P2(US1 的必要配套、本身不引入新安全能力)。

**Independent Test**: 觸發 US1(舊 session 被取代)後,於舊處操作 → 觀察到明確「账号在他处登录」提示 + 自動回登入頁;期間不發生重複的自動換新嘗試或卡住。

**Acceptance Scenarios**:

1. **Given** 一個已被取代(失效)的舊 session, **When** 它發出受保護操作, **Then** 使用者看到「账号在他处登录」訊息並被導回登入頁。
2. **Given** 舊 session 被取代, **When** 前端嘗試以該 session 的憑證自動換新(refresh)以恢復, **Then** 換新亦被拒、回登出訊號,**不形成無限換新迴圈**。
3. **Given** 舊 session 同時有多個 in-flight 請求皆被取代, **When** 它們各自收到登出訊號, **Then** 使用者**至多看到一次**登出提示(不重複彈窗)、乾淨登出一次。

---

### User Story 4 - 未啟用帳號維持多裝置;啟用帳號的正常單一使用不被誤踢 (Priority: P2)

身為一般使用者,我希望:(a) 若我的帳號**未啟用**單一-session,我能像現在一樣在多個裝置/分頁同時登入;(b) 若我的帳號**已啟用**單一-session,只要我**只用一處**正常操作(包含長時間使用、憑證在背景自動換新),**絕不會被莫名踢出**。

**Why this priority**: 確保本 feature 不造成行為回歸 —— 未啟用帳號零變化、啟用帳號的正常單一使用零誤判。P2(US1/US2 的正確性邊界)。

**Independent Test**: (a) 未啟用帳號於兩分頁登入操作皆正常;(b) 啟用帳號於單一分頁長時間操作(跨越憑證自動換新)始終正常、不被登出。

**Acceptance Scenarios**:

1. **Given** 一個未啟用單一-session 的帳號, **When** 它在多個分頁/裝置登入並操作, **Then** 全部正常並存(維持升級前行為)。
2. **Given** 一個已啟用單一-session 的帳號只在一處使用, **When** 其憑證隨時間自動換新後繼續操作, **Then** 始終有效、不被誤判踢出(session 跨換新存活)。

---

### User Story 5 - 部署過渡:既有登入 session 一次性乾淨重新登入 (Priority: P3)

身為本 feature 落地當下已登入的使用者,我接受**一次性的重新登入**:升級導入了新的 session 識別,落地前簽發的憑證無對應識別,首次操作/換新時被乾淨登出、重新登入一次即恢復正常。

**Why this priority**: 既有不變式的過渡驗收(一次性、資料無損),非新能力;優先序最低。

**Independent Test**: 持一張落地前簽發的有效憑證,於落地後操作 → 被乾淨登出、重新登入後一切正常(僅此一次)。

**Acceptance Scenarios**:

1. **Given** 一張本 feature 落地前簽發、仍在有效期內的憑證, **When** 落地後以它操作或自動換新, **Then** 被乾淨登出、提示重新登入(一次性、資料無損),重新登入後正常。

### Edge Cases

- **未啟用 vs 啟用的界線**:同一次「多處登入」在未啟用帳號 = 合法並存;在啟用帳號 = 後登入取代先登入。界線由該帳號解析後的 policy(繼承系統預設 / 開 / 關)決定。
- **取代與換新的交互**:被取代的舊 session 既不能直接操作、也不能透過憑證自動換新「復活」;兩條路徑都導向乾淨登出(避免「踢出→換新→又被踢」的迴圈)。
- **服務重啟**:單一-session 的「當前有效 session」狀態須在服務重啟後仍正確,不得因重啟造成全站非預期登出。
- **政策切換的即時性**:把某帳號從「關」改「開」後,該帳號既有的多個並存 session 在後續操作時收斂為「僅最新登入有效」;從「開」改「關」後恢復多裝置並存。
- **被取代 session 的殘留憑證**:舊 session 的換新憑證即使技術上未到期,亦因不再是「當前有效 session」而被拒;不依賴憑證自然到期才失效。
- **帳號間互不影響**:對某帳號的登入/政策變更,絕不影響其他帳號的 session(嚴格隔離)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 支援**逐帳號**的單一-session 政策,取值為三態之一:繼承系統預設 / 強制啟用 / 強制停用;並 MUST 提供一個**全站預設**值。帳號的有效政策 = 繼承時取系統預設,否則取該帳號覆寫值。
- **FR-002**: 當帳號有效政策為**啟用**時,該帳號成功登入 MUST 使其**先前所有 session 立即失效**;任何時刻該帳號至多一個有效 session(最新登入者)。
- **FR-003**: 被取代(失效)的 session 在其後續任一受保護請求 MUST 收到「帳號已在他處登入」之登出訊號(對應前端顯示提示後乾淨登出並導回登入)。此訊號 MUST NOT 觸發前端的憑證自動換新重試(以免形成迴圈)。
- **FR-004**: 被取代的 session MUST NOT 能透過憑證自動換新(refresh)復活;其換新請求 MUST 同樣回登出訊號。
- **FR-005**: 當帳號有效政策為**停用**(含 028 全站預設)時,系統 MUST 維持升級前的多裝置/多登入並存行為(不踢、不限制)。
- **FR-006**: 對啟用帳號的**正常單一使用**(只在一處、含憑證隨時間自動換新)MUST NOT 被誤判為他處登入而踢出;同一 session MUST 能跨多次自動換新持續有效。
- **FR-007**: 028 全站預設 MUST 為**停用**(dormant 上線):既有多裝置使用者**除一次性重新登入(FR-011)外**不受影響;啟用單一-session 在 028 由後端設定完成(圖形管理介面屬後續 029、不在本 feature)。
- **FR-008**: 政策變更(將某帳號設為啟用/停用)MUST 只影響**該帳號**的後續登入/請求判定,MUST NOT 影響其他帳號(嚴格帳號隔離)。
- **FR-009**: 本 feature MUST 維持 **wire 中性**:登入/換新成功回應的結構**逐字不變**、MUST NOT 新增任何對外端點、MUST NOT 變更前端(base-web)。
- **FR-010**: 「帳號已在他處登入」登出訊號 MUST 使用既有的「他處登入」回應碼(`7777`);所有被取代/失效路徑 MUST NOT 回 `3333` / `9999` / `9998`(沿既有避免登出 dead loop 紀律)。
- **FR-011**: 部署過渡:本 feature 落地前簽發、仍有效的既有憑證 MUST 觸發**一次性**乾淨重新登入(資料無損;不另做相容墊片)。
- **FR-012**: 單一-session 的「帳號當前有效 session」狀態 MUST **持久**(服務重啟後判定仍正確、不致全站非預期登出);且讀取此狀態 MUST 為**每請求廉價可行**(不顯著增加受保護請求延遲)。
- **FR-013**: 本 feature MUST NOT 實作「每裝置一個 session」(多裝置各自保有一 session、僅同裝置重登互相取代)—— 該語義需裝置識別、屬不同軸的獨立後續;本 feature 的「停用」即代表多裝置並存。
- **FR-014**: 本 feature MUST NOT 新增登出端點;登出維持僅由前端清除狀態(沿既有設計)。被取代的 session 之失效**僅由新登入觸發**(非由登出端點)。
- **FR-015**: 「帳號有效政策解析(三態 × 系統預設 → 啟用/停用)」MUST 有單元測試覆蓋全部分支。

### Key Entities *(include if feature involves data)*

- **單一-session 政策(session policy)**:描述某帳號是否套用單一-session。屬性:逐帳號取值(繼承 / 啟用 / 停用)+ 一個全站預設值。決定該帳號是否適用 FR-002 的登入收斂。
- **帳號當前有效 session 指標(current-session pointer)**:代表「某帳號目前唯一有效的那一次登入」之識別。每次成功登入更新為最新登入的 session 身分;每個受保護請求據此判定「此請求的憑證是否屬當前有效 session」。需持久且每請求可廉價讀取。
- **session 身分(session identity)**:一次登入所建立、寫入該次登入所發憑證內的識別;同一 session 的憑證自動換新沿用同一身分(故正常單一使用跨換新存活);新登入產生新身分。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 啟用單一-session 的帳號,在第二處成功登入後,第一處於下一個操作 **100%** 被登出 —— 任何時刻該帳號至多一個有效 session。
- **SC-002**: 被取代的 session 登出時,使用者看到明確「账号在他处登录」提示並回到登入頁,**0 次**無限重試 / 卡死 / 無聲失敗;同時多個 in-flight 請求至多彈一次提示。
- **SC-003**: 啟用單一-session 的帳號**正常單一使用**(含長時間、跨憑證自動換新)造成 **0 次**誤登出。
- **SC-004**: 未啟用(含 028 全站預設停用)的帳號維持多裝置並存,行為與升級前 **0 差異**。
- **SC-005**: 028 上線後,除**一次性**重新登入(FR-011)外,對既有使用者 **0 行為變化**(預設停用、dormant)。
- **SC-006**: 登入/換新成功回應結構與升級前 **0 差異**;被取代/失效路徑回應中 `3333` / `9999` / `9998` 出現次數為 **0**(一律「他處登入」碼 `7777`)。
- **SC-007**: 服務重啟後,啟用帳號的單一-session 判定 **100%** 仍正確(不因重啟造成全站非預期登出)。
- **SC-008**: 守恆不破 —— 既有後端單元測試前後全綠(加新測)、**不新增任何對外端點**、新增的資料欄遷移可逆。

## Assumptions

- **全站預設 = 停用、帳號預設 = 繼承**:028 上線後全員解析為「停用」(dormant),需要的帳號才個別啟用。
- **028 政策由後端設定**:每帳號政策 + 系統預設在 028 經後端(資料/設定)控制;**圖形管理介面(系統預設 runtime 可調 + 使用者管理頁逐帳號設定)為後續 feature 029**,疊在本 feature 的政策儲存之上。
- **前端已能處理「他處登入」碼**:base-web 既有的回應碼處理已支援「他處登入」(`7777`)→ 顯示提示 + 乾淨登出,故 wire 契約不變、前端零改。
- **既有換新 / 登入流程為基礎**:沿用既有登入與憑證自動換新流程;本 feature 在其上加「當前有效 session」判定。
- **持久層為真相、快取為熱路徑**:「當前有效 session」狀態以持久儲存為準(服務重啟不丟),另以快取支撐每請求廉價讀取;快取遺失時自持久層回填、不致誤登出。
- **單實例為主**:現行部署為單實例;持久層使多實例下的判定一致性正交可行,但多實例調校不在本 feature 重點。
- **access 端由 stateless 轉為可被 session 撤銷**:沿既有「授權每請求讀最新狀態」的先例(角色即時失效);本 feature 為同軸延伸、非破壞既有不變式。
- **「每裝置一個 session」為獨立後續**:需穩定的裝置識別(屬不同軸),不在本 feature;本 feature 的「停用」即多裝置並存。
- **rust-api 單倉**:全部變動在後端;不新增對外端點、不動前端、不動權限政策、不分岔第三方套件、不新增建置單元。
