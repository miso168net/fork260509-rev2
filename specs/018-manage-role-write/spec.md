# Feature Specification: Manage Role Write (CRUD)

**Feature Branch**: `018-manage-role-write`

**Created**: 2026-06-02

**Status**: Draft

**Input**: User description: "Phase 4 主流業務 — 角色管理頁的寫端 CRUD(新增/編輯/刪除/批次刪除角色),把 016 唯讀 role list 閉成完整 CRUD,並讓角色「啟用/停用」真正生效。凍結設計來源:[`docs/superpowers/018-manage-role-write.md`](../../docs/superpowers/018-manage-role-write.md)(Phase 0 brainstorm,D1–D5 user 親決)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新增角色 (Priority: P1)

身為系統維運者(最高權限管理員),我希望在「角色管理」頁新增一個角色(填角色名稱、角色代碼、描述、啟用狀態),以便建立新的權限分組供指派給使用者。

**Why this priority**: 這是寫端的核心可見價值 —— 016 之後管理頁「看得到」角色但還不能「新增」。能新增角色是把角色管理頁從唯讀變可管理的第一步,且立起「寫入 + 稽核 + 授權把關 + 缺欄補實」這套後續角色寫端共用骨架,可單獨交付即構成可用的新增能力。

**Independent Test**: 以最高權限管理員身分,**使用既有角色管理頁的既有新增控制項**(無新增畫面)填妥資料並送出 → 列表多一筆該角色(帶描述、啟用狀態);以非最高權限身分嘗試新增則被拒。

**Acceptance Scenarios**:

1. **Given** 一個最高權限管理員, **When** 填妥角色名稱/代碼/描述/狀態並送出新增, **Then** 系統建立該角色、列表出現該筆、輸出識別碼為字串,並記錄一筆稽核(誰、何時、新增)。
2. **Given** 一個最高權限管理員, **When** 以一個與現有有效角色相同的角色代碼新增, **Then** 被拒並回傳業務錯誤(回結構化錯誤、HTTP 非 5xx、不崩潰、不寫入半筆)。
3. **Given** 一個非最高權限的已登入者(或未認證請求), **When** 嘗試新增角色, **Then** 被拒(權限不足 / 未認證),不建立任何資料。
4. **Given** 一個最高權限管理員, **When** 以與現有角色**相同的角色名稱但不同的角色代碼**新增, **Then** 成功建立(角色名稱不要求唯一,唯一性僅限角色代碼)。

### User Story 2 - 編輯角色 (Priority: P2)

身為系統維運者,我希望能編輯既有角色的名稱、描述與啟用狀態,以便維護權限分組;並能把不再使用的角色設為停用。

**Why this priority**: 與新增同屬角色管理核心維運能力,沿用 US1 立起的寫入 + 稽核骨架(同一表單、編輯模式);可獨立於 US1 驗證(改既有筆、不建新筆)。優先序次於新增,因「先能建、再能改」的自然順序。

**Independent Test**: 以管理員身分對既有角色開編輯、改名稱與描述並送出 → 該筆顯示更新後的值;把某自訂角色設為停用 → 該角色不再出現於指派選項、且其權限不再對持有者生效(但仍顯示於管理列表供重新啟用)。

**Acceptance Scenarios**:

1. **Given** 一個最高權限管理員與一個既有角色, **When** 修改該角色的名稱/描述/狀態並送出, **Then** 該筆更新為新值,並記錄一筆稽核(誰、何時、修改)。
2. **Given** 一個最高權限管理員, **When** 編輯時嘗試變更角色代碼, **Then** 角色代碼維持不變(代碼為建立後固定的穩定識別,僅於新增設定)。
3. **Given** 一個最高權限管理員與一個自訂角色, **When** 把該角色設為停用, **Then** 該角色於後續授權檢查不再對其持有者授予權限、且不再出現於指派選項,但**仍顯示於角色管理列表(狀態為停用)**供重新啟用。
4. **Given** 一個先前被停用的自訂角色, **When** 重新啟用, **Then** 該角色恢復可被指派、且其權限於後續授權檢查重新對持有者生效。
5. **Given** 一個最高權限管理員與一個系統內建種子角色, **When** 編輯時嘗試把該種子角色設為停用, **Then** 被拒(回業務錯誤),其狀態維持啟用。
6. **Given** 一個最高權限管理員與一個系統內建種子角色, **When** 只修改該種子角色的名稱或描述(不動狀態), **Then** 允許並更新成功(種子保護只擋刪除與停用,不擋名稱/描述編輯)。
7. **Given** 一個最高權限管理員, **When** 編輯一個不存在或已軟刪的角色, **Then** 回業務錯誤、不發生任何資料變動。
8. **Given** 一個非最高權限身分, **When** 嘗試編輯角色, **Then** 被拒。

### User Story 3 - 刪除角色(含批次) (Priority: P3)

身為系統維運者,我希望能刪除單一或多個自訂角色,以便移除不再需要的權限分組。刪除為可復原的軟刪除;且不可刪除系統內建的種子角色,以免破壞權限骨幹。

**Why this priority**: 完成 CRUD 閉環的最後一塊。價值依附於前兩個故事(先有角色才談移除),且刪除涉及「種子保護」與「可復原」兩個安全考量,故列 P3。

**Independent Test**: 以管理員身分刪除一個(或勾選多個)自訂角色 → 被刪者不再出現於有效列表、資料可復原;嘗試刪除內建種子角色時被拒。

**Acceptance Scenarios**:

1. **Given** 一個最高權限管理員與一個既有自訂角色, **When** 刪除該角色, **Then** 該筆從有效列表消失(軟刪、可復原)、不再可指派或授權,並記錄一筆稽核(誰、何時、刪除)。
2. **Given** 一個最高權限管理員勾選多個自訂角色, **When** 批次刪除, **Then** 這些角色皆從有效列表消失、各記一筆稽核,且該批次的多筆稽核時間一致。
3. **Given** 一個最高權限管理員, **When** 刪除目標包含系統內建種子角色(單筆或批次中含種子), **Then** 被拒(回業務錯誤),且該操作不刪除任何角色(全部仍在)。
4. **Given** 一個最高權限管理員, **When** 刪除一個不存在或已軟刪的角色, **Then** 回業務錯誤、不發生任何資料變動。
5. **Given** 一個最高權限管理員, **When** 批次刪除未勾選任何角色(空清單), **Then** 無操作(no-op)、不報錯、不變動資料。
6. **Given** 一個非最高權限身分, **When** 嘗試刪除角色, **Then** 被拒。

---

### Edge Cases

- **角色代碼重複**:新增時角色代碼與現有有效角色衝突 → 回業務錯誤、不寫入(US1-2)。角色名稱不要求唯一(US1-4)。
- **軟刪角色的代碼重用**:角色代碼唯一性僅限**有效(未刪除)角色之間**;一個已軟刪角色的代碼,可被新角色重新使用。角色「復原」不在本 feature 範圍(本 feature 只提供軟刪、不提供復原入口)。
- **刪/停用種子角色**:刪除或停用系統內建種子角色 → 被拒;批次中含種子 → **整批拒、無部分執行**(US3-3)。種子角色的名稱/描述編輯仍允許(US2-6)。
- **目標不存在**:編輯或刪除一個不存在或已軟刪的角色 → 回業務錯誤、不寫入(US2-7、US3-4)。
- **軟刪後不現於有效列表**:被刪角色不出現在 016 的角色列表(只列有效),但資料保留。
- **停用角色的可見性**:停用角色**仍顯示於角色管理列表**(供管理員重新啟用),但**不出現於指派選項**、也不對持有者授予權限。
- **批次空清單**:批次刪除未勾選任何角色 → 無操作(no-op)、不報錯(US3-5)。
- **回歸:既有指派路徑遇停用/已刪角色**(觸發點在既有使用者寫端、非本 feature 新行為):既有的「指派角色給使用者」流程在角色被本 feature 停用/軟刪後 MUST 只採計有效角色、略過無效者、不崩潰 —— 由本 feature 對「角色取用共同來源」的調整間接保證,以回歸測試覆蓋。
- **權限不足 vs 未認證**:已認證但非最高權限 → 權限不足拒絕;未帶/無效憑證 → 未認證拒絕(兩者區分)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓最高權限管理員新增角色,輸入為:角色名稱、角色代碼、描述、啟用狀態(此四欄,不引入此四欄以外的新輸入欄位);新增成功後該角色出現於角色列表。
- **FR-002**: 角色代碼 MUST 在**有效(未刪除)角色**之間唯一;新增時與有效角色代碼重複 MUST 被拒並回業務錯誤(不崩潰、不寫入半筆)。角色名稱 MUST NOT 要求唯一。已軟刪角色的代碼 MAY 被新角色重用(唯一性僅限有效角色間)。
- **FR-003**: 系統 MUST 讓管理員編輯既有角色的名稱、描述與啟用狀態;編輯 MUST NOT 變更其**角色代碼**(代碼為建立後固定、僅於新增設定與檢查唯一)。
- **FR-004**: 系統 MUST 讓管理員刪除單一或多個角色(種子角色之保護見 FR-005),刪除為**可復原(軟刪除)**;被刪者 MUST NOT 出現於有效(未刪除)列表。
- **FR-005**: 系統 MUST 阻止刪除**或**停用系統內建種子角色(以角色代碼 `R_SUPER` / `R_ADMIN` / `R_USER_COMMON` 識別的三個系統角色 —— 它們是權限骨幹,刪或停用會使系統失去授權能力);此類操作(單筆或批次中含種子)MUST 整個被拒,且不影響任何角色。種子身分**以角色代碼識別**(代碼不可改);種子角色仍 MUST 允許編輯其名稱與描述(種子保護**只擋刪除與停用**,不擋名稱/描述編輯)。
- **FR-006**: 角色啟用狀態 MUST 生效:被設為**停用**(或已軟刪)的角色 MUST NOT 可被指派給使用者,且其權限 MUST NOT 於**後續授權檢查**對其持有者生效;重新啟用後恢復。生效作用於停用後的後續授權檢查(預期不需等待持有者重新登入);立即撤銷既有、進行中的請求不在本範圍。
- **FR-007**: 每筆新增 / 編輯 / 刪除 MUST 留下稽核紀錄(誰執行、何時、何種操作、對哪個角色);稽核所記的操作時間 MUST 與該筆角色對應的時間欄位(建立/更新/刪除時間)同源一致,且**同一次批次操作所產生的多筆稽核時間 MUST 一致**(以此作為「時間記錄來自單一一致來源」的可觀測判準)。
- **FR-008**: 新增 / 編輯 / 刪除角色的寫入能力 MUST 僅限最高權限管理員;其他已認證使用者 MUST 被拒(權限不足),未認證請求 MUST 一律被拒。
- **FR-009**: 系統 MUST 儲存角色管理列表先前無來源而顯示為空白的欄位(描述、啟用狀態,以及建立/更新的時間與操作者),使新建或編輯後的角色於列表顯示真實值而非空白。
- **FR-010**: 對外輸出的識別碼 MUST 維持**字串**形式;寫端回應 MUST 對齊既有對外資料契約(成功 / 業務錯誤代碼)。本 feature 的業務規則違反(代碼重複、刪或停用種子、目標不存在、非法輸入)MUST 回結構化業務錯誤(統一回應格式、含業務錯誤碼、HTTP 非 5xx);各類違反所對應的確切錯誤碼於規劃階段對照既有代碼矩陣定。
- **FR-011**: 本 feature MUST 沿用既有前端角色管理頁與其新增/編輯/刪除控制項,僅將其既有的呼叫接點接上後端,MUST NOT 新增前端畫面或變更既有畫面/表單結構。
- **FR-012**: 角色管理列表 MUST 顯示停用角色(供管理員辨識並重新啟用),但 MUST NOT 顯示已軟刪角色。

### Key Entities *(include if feature involves data)*

- **角色(Role)**:一組權限分組 —— 角色名稱、角色代碼(建立後固定的穩定唯一識別)、描述、啟用狀態,以及建立/更新/刪除的時間與操作者(稽核中介資料)。系統內建三個種子角色(以角色代碼 `R_SUPER` / `R_ADMIN` / `R_USER_COMMON` 識別)為權限骨幹、受保護;種子身分以代碼識別(代碼不可改),其顯示名稱仍可編輯。
- **使用者—角色指派(User-Role assignment)**:使用者持有哪些角色;停用或已軟刪的角色 MUST NOT 納入有效指派(不可新指派、且不對持有者授權)。本 feature 不改使用者層的指派流程,只定義「停用/刪除角色」對既有與未來指派的效果。
- **稽核紀錄(Audit record)**:每筆新增/編輯/刪除對應一筆「誰、何時、何操作、對哪個角色」的不可改事件。

## Success Criteria *(mandatory)*

> 下列百分比(100% / 0%)指對所列舉的代表性 case 矩陣**全數通過**(各類正反例至少各一),非統計抽樣。

### Measurable Outcomes

- **SC-001**: 管理員能新增角色(含描述與啟用狀態)並在列表看到該筆出現。
- **SC-002**: 管理員能編輯既有角色的名稱/描述/狀態,列表反映更新後的值;角色代碼維持不變(0% 編輯操作改動角色代碼)。
- **SC-003**: 管理員能刪除單一或多個自訂角色,被刪者不再出現於有效列表,且資料保留可供日後復原。
- **SC-004**: 寫入授權把關正確:**在合法輸入前提下**最高權限者寫入成功率 100%;其他已認證使用者與未認證請求的寫入被拒比例 100%(0% 未授權寫入成功)。
- **SC-005**: 100% 的新增/編輯/刪除操作各產生恰一筆稽核紀錄(含操作者、時間、操作類型);批次刪除 N 筆產生 N 筆,且該批次的稽核時間一致。
- **SC-006**: 系統內建種子角色無法被刪除或停用(此類嘗試成功率 0%,且不誤動其他角色);但種子角色的名稱/描述編輯成功率 100%。
- **SC-007**: 以重複角色代碼新增被清楚拒絕(0% 造成崩潰或半筆寫入);以相同名稱不同代碼新增則成功。
- **SC-008**: 經本 feature 新建/編輯的角色,於角色管理頁顯示真實的描述/狀態/建立資訊,而非 016 的空白。
- **SC-009**: 停用(或軟刪)的角色不可被指派、且其權限於後續授權檢查不再對持有者生效 —— 以一個僅該角色可達的受保護操作驗證:停用後(取得後續授權檢查時)該存取被拒(停用角色仍授予存取或仍可被指派的比例 0%);重新啟用後恢復。in-flight / 既有進行中請求不在量測範圍。
- **SC-010**: 停用角色 100% 仍出現於角色管理列表(供重新啟用)、已軟刪角色 0% 出現於該列表;且本 feature 不新增任何前端畫面、不變更既有角色管理頁的表單/控制項結構(僅將既有控制項接上後端)。
- **SC-011**: 既有的使用者寫端(新增/編輯/刪除使用者)行為、既有授權把關、選單可見性與列表顯示,於本 feature 改動(角色取用共同來源 + 稽核時間源校正)後 100% 不被破壞(回歸)。

## Assumptions

- **種子角色保護**(D1):種子角色 = 系統內建、以角色代碼 `R_SUPER` / `R_ADMIN` / `R_USER_COMMON` 識別的三個角色(代碼為穩定識別、不可改),為權限骨幹;本 feature 只做「不可刪、不可停用、但可改名稱/描述」的最小保護(因停用等同使其授權失效、與刪除同樣會破壞骨幹),更廣的受保護角色策略留後續 feature。
- **軟刪除 + 可復原**(D4):刪除為可復原的軟刪除;刪除或停用角色 MUST NOT 清除既有的使用者—角色指派紀錄、**亦不撤除既有的授權規則** —— 一律改以「只採有效角色」的過濾達成「不授權 / 不可指派」,重新啟用即恢復(過濾優先、不動底層紀錄)。本 feature 提供軟刪但不提供復原入口(復原屬後續)。
- **角色代碼建立後不可改**(D2):角色代碼為授權與指派解析的穩定鍵,僅於新增設定 + 檢查唯一性;編輯不改角色代碼(前端編輯模式該欄唯讀屬實作接線細節)。
- **停用角色語意與生效時機**(D3):停用角色保留於管理列表供重啟用;其「不可指派 / 不授權」於授權把關時生效。**預期**以「角色取用處統一只吃有效角色集」達成後續授權檢查即時生效(不需等持有者重新登入);**確切的取角色來源與生效時機於規劃階段對照既有授權實作確認**;立即撤銷既有、進行中請求不在本範圍。
- **寫端授權 = 最高權限**:新增/編輯/刪除僅限最高權限管理員;一般管理員可讀但不可寫(對齊既有授權把關機制)。
- **缺欄補實(承 016)**:016 為唯讀、對未儲存欄回空值;本 feature 為使這些欄可被新增/編輯而補齊其儲存,屬「角色寫端」這一波一次補齊,避免反覆變更資料結構。
- **對外識別碼為字串**:對外識別碼 MUST 維持字串形式,對齊既有對外資料契約凍結值(內部表示與轉換時機交由規劃/資料模型階段決定)。
- **業務規則錯誤代碼**:代碼重複 / 刪或停用種子 / 目標不存在 / 非法輸入等業務規則違反,回用既有的業務錯誤代碼(對齊既有錯誤碼矩陣);詳細代碼於規劃階段對照既有契約確認。
- **稽核時間源一致**:稽核所記操作時間以單一一致來源記錄,並與既有使用者寫端的稽核時間記錄方式對齊一致(現有使用者寫端的部分時間源不一致一併校正,屬本波附帶範圍 —— 含其新增/編輯/刪除的回歸驗證,見 SC-011)。
- **沿用既有能力**:沿用既有統一回應格式與錯誤碼、授權把關、軟刪除過濾邊界、稽核寫入機制、既有資料存取慣例;前端沿用既有管理頁(僅接線既有控制項,屬已授權的前端受管軌道)。
- **跨既有能力的觸及與回歸範圍**:讓「停用/軟刪角色不授權、不可指派」生效,需調整既有「角色取用共同來源」—— 具體觸及:授權把關取角色、選單可見性過濾、角色列表與指派下拉、使用者資訊組裝、以及既有使用者寫端的稽核時間源;以上皆 MUST 回歸驗證既有授權與顯示行為不被破壞(見 SC-011)。觸及面與回歸測試清單於規劃階段界定。
