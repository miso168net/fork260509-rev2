# Feature Specification: Manage User Write (CRUD)

**Feature Branch**: `017-manage-user-write`

**Created**: 2026-06-01

**Status**: Draft

**Input**: User description: "Phase 4 主流業務 — 使用者管理頁的寫端 CRUD(新增/編輯/刪除/批次刪除使用者),讓管理員真的能管理使用者(016 唯讀 list 之後的閉環)。凍結設計來源:[`docs/superpowers/017-manage-user-write.md`](../../docs/superpowers/017-manage-user-write.md)(Phase 0 brainstorm,D1–D9 user 親決)"

## Clarifications

### Session 2026-06-01

- Q: 編輯使用者時,帳號名(userName)可否修改? → A: **不可改(immutable)**;userName 建立後固定,編輯只改 profile/角色/狀態,唯一性僅於新增檢查(前端編輯模式該欄唯讀屬 plan 接線細節)。
- Q: 把使用者設為「停用(status=disabled)」時,要不要擋住其登入? → A: **要 enforce**;017 於登入把關讓 `status=disabled` 的使用者**無法登入**(動既有登入路徑加 status 檢查)。確切拒絕 wire code(對齊既有代碼矩陣、與既有 no-enumeration 取捨)留規劃階段定;enforcement 作用於登入入口,已簽發未過期的工作階段依效期自然失效(立即撤銷 session 不在本範圍)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新增使用者 (Priority: P1)

身為系統維運者(高權限管理員),我希望在「使用者管理」頁能新增一個使用者(填帳號、暱稱、性別、電話、電子郵件、所屬角色、啟用狀態),以便把新成員納入系統。新使用者由系統指派一組預設登入憑證(表單不收密碼)。

**Why this priority**: 這是寫端的核心可見價值 —— 016 之後管理頁「看得到」使用者但還不能「新增」。能新增使用者是把管理頁從唯讀變成可管理的第一步,且立起「寫入 + 角色指派 + 稽核 + 授權把關」這套後續寫端共用的骨架,可單獨交付即構成一個可用的新增能力。

**Independent Test**: 以高權限管理員身分,在新增表單填妥資料並送出 → 列表多一筆該使用者(帶角色、性別/電郵等顯示值);該使用者可用系統指派的預設憑證登入;以非高權限身分嘗試新增則被拒。

**Acceptance Scenarios**:

1. **Given** 一個高權限管理員, **When** 填妥帳號/暱稱/性別/電話/電郵/角色/狀態並送出新增, **Then** 系統建立該使用者(含所選角色指派)、列表出現該筆、輸出識別碼為字串、不外洩憑證,並記錄一筆稽核(誰、何時、新增)。
2. **Given** 一個高權限管理員, **When** 以一個與現有有效使用者相同的帳號名新增, **Then** 被拒並回傳清楚的業務錯誤訊息(不崩潰、不寫入半筆)。
3. **Given** 一個非高權限的已登入者(或未認證請求), **When** 嘗試新增使用者, **Then** 被拒(權限不足 / 未認證),不建立任何資料。

---

### User Story 2 - 編輯使用者 (Priority: P2)

身為系統維運者,我希望能編輯既有使用者的暱稱、性別、電話、電子郵件、啟用狀態與所屬角色,以便維護成員資料與權限。

**Why this priority**: 與新增同屬管理頁核心維運能力,沿用 US1 立起的寫入 + 角色指派 + 稽核骨架(同一表單、編輯模式);可獨立於 US1 驗證(改既有筆、不建新筆)。優先序次於新增,因「先能建、再能改」的自然順序。

**Independent Test**: 以管理員身分對既有使用者開編輯、改暱稱與角色並送出 → 該筆顯示更新後的值與角色;編輯不改動其登入憑證。

**Acceptance Scenarios**:

1. **Given** 一個高權限管理員與一個既有使用者, **When** 修改該使用者的暱稱/性別/電話/電郵/狀態/角色並送出, **Then** 該筆更新為新值、角色指派整批替換為新選擇,並記錄一筆稽核(誰、何時、修改);其登入憑證不變。
2. **Given** 一個高權限管理員, **When** 編輯時指派的角色清單含無效(不存在 / 已刪)的角色, **Then** 系統只採計有效角色、不崩潰。
3. **Given** 一個非高權限身分, **When** 嘗試編輯使用者, **Then** 被拒。

---

### User Story 3 - 刪除使用者(含批次) (Priority: P3)

身為系統維運者,我希望能刪除單一或多個使用者,以便移除離職或誤建的帳號。刪除為可復原的軟刪除;且不可刪除自己,以免把自己鎖在系統外。

**Why this priority**: 完成 CRUD 閉環的最後一塊。價值依附於前兩個故事(先有資料才談移除),且刪除涉及「自我保護」與「可復原」兩個安全考量,故列 P3。

**Independent Test**: 以管理員身分刪除一個(或勾選多個)使用者 → 被刪者不再出現於有效列表、資料可復原;嘗試刪除自己時被拒。

**Acceptance Scenarios**:

1. **Given** 一個高權限管理員與一個既有使用者(非自己), **When** 刪除該使用者, **Then** 該筆從有效列表消失(軟刪、可復原),並記錄一筆稽核(誰、何時、刪除)。
2. **Given** 一個高權限管理員勾選多個使用者(皆非自己), **When** 批次刪除, **Then** 這些使用者皆從有效列表消失、各記一筆稽核。
3. **Given** 一個高權限管理員, **When** 刪除目標包含自己(單筆或批次中含自身), **Then** 被拒(回業務錯誤),且該操作不刪除任何人(自身仍在)。
4. **Given** 一個非高權限身分, **When** 嘗試刪除使用者, **Then** 被拒。

---

### Edge Cases

- **帳號名重複**:新增時帳號名與現有有效使用者衝突 → 回業務錯誤、不寫入(US1-2)。
- **刪除自己**:單筆或批次含 operator 本人 → 整個操作被拒、無人被刪(US3-3、D7)。
- **軟刪後不現於列表**:被刪使用者不出現在 016 的使用者列表(只列有效),但資料保留可復原。
- **角色指派含無效碼**:指派不存在/已刪角色 → 只採有效者、不報錯崩潰(US2-2)。
- **缺欄補實**:016 唯讀列表對性別/電郵/電話/狀態/建立資訊回空值;本 feature 寫入後這些欄有真實值,新建/編輯的使用者列表顯示實際資料。
- **權限不足 vs 未認證**:已認證但非高權限 → 權限不足拒絕;未帶/無效憑證 → 未認證拒絕(兩者區分)。
- **預設憑證**:新使用者由系統指派預設登入憑證(表單不收);變更憑證屬另案。
- **停用使用者登入**:被設為停用(status=disabled)的使用者嘗試登入 → 被拒(FR-013、登入入口 enforce);其已登入且未過期的工作階段於到期前可能仍有效(立即撤銷不在本範圍)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓具最高權限的管理員新增使用者,輸入至少含:帳號、暱稱、性別、電話、電子郵件、所屬角色清單、啟用狀態;新增成功後該使用者出現於使用者列表。
- **FR-002**: 新增使用者時,系統 MUST 為其指派一組系統預設登入憑證(新增表單不收憑證);變更/設定憑證的流程 MUST NOT 在本 feature 範圍。
- **FR-003**: 系統 MUST 讓管理員編輯既有使用者的暱稱、性別、電話、電子郵件、啟用狀態與所屬角色;編輯 MUST NOT 變更其**帳號名**(userName 建立後不可改、唯一性僅於新增檢查)與**登入憑證**。
- **FR-004**: 系統 MUST 讓管理員刪除單一或多個使用者,刪除為**可復原(軟刪除)**;被刪者 MUST NOT 出現於有效(未刪除)列表。
- **FR-005**: 系統 MUST 阻止 operator 刪除自己的帳號(單筆或批次中含自身皆拒,且該操作不刪除任何人)。
- **FR-006**: 使用者帳號名 MUST 在有效使用者間唯一;新增時帳號名重複 MUST 被拒並回清楚的業務錯誤(不崩潰、不寫入半筆)。
- **FR-007**: 角色指派 MUST 只連結既有有效角色;編輯時 MUST 以新選擇整批替換該使用者的角色指派。
- **FR-008**: 每筆新增 / 編輯 / 刪除 MUST 留下稽核紀錄(誰執行、何時、何種操作)。
- **FR-009**: 新增 / 編輯 / 刪除使用者的寫入能力 MUST 僅限具最高權限的管理員;其他已認證使用者 MUST 被拒(權限不足),未認證請求 MUST 一律被拒。
- **FR-010**: 系統 MUST 儲存使用者管理頁所顯示但目前(016)無來源資料的欄位(性別 / 電話 / 電子郵件 / 啟用狀態,以及建立/更新的時間與操作者),使新建或編輯後的使用者於列表顯示真實值而非空白。
- **FR-011**: 對外輸出的識別碼 MUST 維持**字串**形式;寫端回應信封 MUST 對齊既有對外資料契約(成功 / 業務錯誤代碼);本 feature 的業務規則錯誤(帳號重複、刪除自己)回對應的業務錯誤代碼。
- **FR-012**: 本 feature MUST 沿用前端(base-web)既有的使用者管理頁與其新增/編輯/刪除控制項,僅將其既有的呼叫接點接上後端,MUST NOT 新增前端畫面或變更既有畫面結構。
- **FR-013**: 使用者啟用狀態 MUST 於登入把關生效:被設為「停用」的使用者 MUST 被拒絕登入(enforcement 作用於登入入口)。已簽發、未過期的工作階段依其效期自然失效;立即撤銷既有工作階段 MUST NOT 在本 feature 範圍。拒絕登入所用的對外代碼 MUST 對齊既有代碼矩陣(確切代碼於規劃階段對照既有 wire 契約與既有 no-enumeration 取捨確認)。

### Key Entities *(include if feature involves data)*

- **使用者(User)**:系統登入主體與其檔案 —— 帳號、暱稱、性別、電話、電子郵件、啟用狀態、所屬角色清單,以及建立/更新/刪除的時間與操作者(稽核中介資料)。登入憑證為系統指派的預設值,不於本 feature 對外輸出或由表單設定。
- **使用者—角色指派(User-Role assignment)**:使用者持有哪些角色;新增/編輯時依所選角色清單建立或整批替換。
- **稽核紀錄(Audit record)**:每筆新增/編輯/刪除對應一筆「誰、何時、何操作、對哪個使用者」的不可改事件。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員能新增使用者(含角色與檔案欄位)並在列表看到該筆出現;新使用者可用系統預設憑證登入。
- **SC-002**: 管理員能編輯既有使用者的檔案欄位與角色,列表反映更新後的值與角色。
- **SC-003**: 管理員能刪除單一或多個使用者,被刪者不再出現於有效列表,且資料可復原。
- **SC-004**: 寫入授權把關正確:具最高權限者寫入成功率 100%;其他已認證使用者與未認證請求的寫入被拒比例 100%(0% 未授權寫入成功)。
- **SC-005**: 100% 的新增/編輯/刪除操作各產生恰一筆稽核紀錄(含操作者、時間、操作類型)。
- **SC-006**: operator 無法刪除自己的帳號(自我刪除嘗試成功率 0%、且該操作不誤刪他人)。
- **SC-007**: 以重複帳號名新增被清楚拒絕(0% 造成崩潰或半筆寫入)。
- **SC-008**: 經本 feature 新建/編輯的使用者,於管理頁顯示真實的性別/電郵/狀態/建立資訊,而非 016 的空白。
- **SC-009**: 被設為停用的使用者無法登入(停用帳號新登入嘗試成功率 0%);編輯時帳號名維持不可改(0% 編輯操作改動 userName)。

## Assumptions

- **預設憑證**(D2):新使用者由系統指派一組預設登入憑證(對齊既有預設帳號慣例);「設定/修改密碼」流程屬獨立的未來 feature,不在本範圍。
- **軟刪除 + 最小自我保護**(D7):刪除為可復原的軟刪除;本 feature 只做「不可刪自己」最小防呆,更廣的受保護使用者(不可刪最高權限種子帳號 / 最後一個高權限者)留後續 feature。
- **寫端授權 = 最高權限**:新增/編輯/刪除僅限最高權限管理員;一般管理員可讀(016)但不可寫(對齊既有授權把關機制)。
- **角色管理本身不在範圍**:管理角色(新增/編輯/刪除角色)屬另一 feature(role 寫端);本 feature 只在使用者層指派既有角色。
- **沿用既有能力**:沿用既有統一回應信封、授權把關、軟刪除過濾邊界、稽核寫入機制、資料存取的單一管道慣例;前端沿用既有管理頁(僅接線既有控制項,屬已授權的 base-web 受管軌道)。
- **缺欄補實(承 016 D2)**:016 為唯讀、對未儲存欄回空值;本 feature 為使這些欄可被新增/編輯而補齊其儲存,屬「新增/修改使用者」這一波一次補齊,避免反覆變更資料結構。
- **對外識別碼為字串**:對齊既有對外資料契約凍結值(對外識別碼字串),內部以整數儲存、於輸出邊界轉字串。
- **業務規則錯誤代碼**:帳號重複 / 刪除自己等業務規則違反,回用既有的業務錯誤代碼(對齊既有信封代碼矩陣);詳細代碼框定於規劃階段對照既有契約確認。
- **停用 enforce 跨入既有登入路徑**(Q2=B):為使「停用」生效,本 feature 於登入把關加 status 檢查,**跨入既有 auth/login(013)**;enforcement 僅於登入入口,既有工作階段依其效期自然失效(立即撤銷 session 留後續)。停用使用者被拒登入的確切對外代碼於規劃階段對照既有代碼矩陣定(既有「账号已被禁用」碼可用,惟其原為 logout 類代碼、用於登入入口的語意與 no-enumeration 取捨於 plan 釐清)。
- **帳號名建立後不可改**(Q1=A):userName 為登入唯一鍵,僅於新增設定 + 檢查唯一性;編輯不改 userName(前端編輯模式該欄唯讀屬 plan 接線細節)。
