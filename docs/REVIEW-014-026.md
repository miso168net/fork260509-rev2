## 2. 必須處理(Critical + 重要 specGap)

**無 Critical、無 confirmed specGap。** 唯一一條對抗驗證後 confirmed 的 blocker 是 025 的 Important bug,列於此:

### 025-I1 · 編輯頂層葉選單會靜默吃掉 component 的 layout 前綴(confirmed · Important · bug)

- **位置**:`base-web/src/views/manage/menu/modules/menu-operate-modal.vue:269`
- **問題**:`effectiveLayout = model.value.parentId === 0 || model.value.menuType === '1' ? layout : ''`。`model.parentId` 在 edit 模式由 rowData 帶入,而 wire 的 `parent_id` 是**字串** `"0"`/`"5"`(§I.3 刻意 type-lie,`Menu.parentId` typing 宣告 number 但 runtime 是 string、`defaultTransform` 不轉型)。對**頂層葉選單**(parentId=`"0"`、menuType=`"2"`)做純編輯(改名/改 order)不碰 parentId 控件直接存檔時,`"0" === 0` 為 false → `effectiveLayout=''` → `transformLayoutAndPageToComponent('', page)` 把 component 的 `layout.X$` 前綴吃掉。
- **真實爆點**:種子 `home`(`component=layout.base$view.home`、`parent_id NULL→"0"`、`menu_type=2`,migration `m20260529_000018:115`)正是這種選單;Super 編輯其名稱/order 後 component 被整欄替換寫回成 `view.home`,破壞其 layout 渲染。
- **為何漏測**:這是 025 引入(020 原 `getSubmitParams` 無條件保留前綴,025 diff `4ad502b4` 新增 `effectiveLayout` gate)的真實 FR-010/SC-005 回歸;acceptance 測資 `cdp_restore` 用 `component:"view.cdp-restore"`(無 layout 前綴)恰好繞過此路徑,typecheck 看到的 parentId 是 number 也抓不到。026 為 rust-api-only、不動 base-web,HEAD 仍含此 bug。
- **修法(對抗驗證者建議)**:頂層判定改 `Number(model.value.parentId) === 0`,或在 `handleInitModel` 把載入的 parentId 正規化為 number(同時修 025-M1 NTreeSelect 預選態);並補一條 acceptance:編輯種子 home(僅改 order)後 psql 驗 `component` 仍 `== layout.base$view.home`。
- **嚴重度判定**:維持 Important 不升 Critical(blast radius 窄:僅頂層葉 + 有 layout 前綴者,種子中僅 home 命中;manage 是目錄=menuType1 安全、巢狀葉 component 無前綴亦安全;可重新編輯帶正確 component 復原、不 crash、不破 auth)。但命中 canonical 種子且觸發門檻低(例行編輯)、明確違反列舉的回歸不變式,不下調為 Minor。

## 4. 跨 feature 主題(比單點 issue 更有價值)

### 4.1 wire id/parentId 字串 type-lie(§I.3 刻意不修)是潛伏地雷,025 首次引爆
014 起 wire `id` 統一回 string、021/025 起 `parentId` 回 string(`"0"`/`"5"`),而 base-web typing 宣告為 `number`(`CommonRecord.id`、`Menu.parentId`),`defaultTransform` 不轉型。016/017 的 type-lie 因 runtime 只走 `NDataTable rowKey`(吃 string|number)而無害(016 crossFeatureNotes、017-I1 皆為已知接受債,DESIGN §11.16);**但 025 首次讓前端對 wire string 做嚴格數值比較(`=== 0`、NTreeSelect number key),把潛伏 type-lie 變成可觀察 data-corruption(025-I1/M1)**。**建議在 DESIGN type-lie 條目補一句鐵律:前端消費端對 wire string id/parentId 一律 `Number()` 正規化後再比較**。這是本批最有價值的跨 feature 教訓。

### 4.2 doc-debt 是壓倒性最常見 finding(13 feature 幾乎全中)
014-M1/M2、015-M1、016-M1、017-M1/I1、018-M1/M2、019-M1/M2/M3、020-M1、021-M1/M3、022-M1/M3、023-M2、025-M2/M3/M4、026-M1/M2 — 主要型態:(a)**spec/data-model/research 與 as-built 的刻意偏差未回填 Deviation Log**(015/016/018/019/025/026);(b)**point-in-time contracts 被後續 feature supersede 而未加 cross-ref**(020 parent_id 被 025 取代、023 count 28→30);(c)**code 註解陳述與 HEAD 行為矛盾**(017 delete handler 寫 POST 實為 DELETE、020-M3 stale 測試敘述)。**模式**:DESIGN(設計權威)回填紀律普遍良好(024/026 皆零 doc-debt 於權威端),債主要積在 per-feature spec 文件,符合本工作流「act on actual code、spec naming 不可盡信」的設計取捨,但仍值得在收尾批次清。

### 4.3 測試分層紀律一致且健康(§I.4)
全批一致採:**純函式 test-first**(SQL-build seam、tree 組裝、cycle 檢查、de_* 反序列化、自鎖 guard、enforcer in-memory 不變式)+ **wiring/形狀對映由 C-V acceptance 覆蓋且 tasks.md 明示「無單元測試」理由**。最有力的證據型態反覆出現:019/020 的逐字回歸 `assert_eq!(json, business_routes())`、021/022/023 的 in-memory enforcer **HARD REPLACE 正交性測試**(`replace_only_touches_X_rows_..._survive`)、023 的 build-time `endpoint_coverage_lint`。**值得固化的觀察**:HARD REPLACE `remove_filtered_policy` 的 v2-維度正交性(menu/button/endpoint 三維共用 casbin_rule 表)是反覆出現的最高風險點,三個 feature 都用「同一 enforcer 同時 seed 三維 → replace 一維驗其餘存活」的單測範式釘死,這是設計上最該保留的鐵律。
