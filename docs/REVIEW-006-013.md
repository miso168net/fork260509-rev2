## 4. 跨 feature 主題（比單點 issue 更有價值）

1. **新增 workspace crate 必須把 prod image build 納 acceptance** — 最反覆的系統性教訓。dev docker bind-mount 會遮住 prod multi-stage Dockerfile 的逐 crate `COPY` 缺口，導致 prod release build 破口逃過 feature acceptance。009 咬過（99356a4 補救）、010 的 Deviation D-1 同源、MEMORY 明載 010/012 也咬過。**紀律修正**：凡加 workspace member 的 feature，`contracts/verification-commands.md` 必含一條 prod target build（`docker compose -f ... -f docker-compose.prod.yml build rust-api` 或 `--target builder`），而非依賴下游 deploy commit 修補。

2. **測試分層策略一致且符合 §3 紀律** — 全線一致：純函式邏輯（JWT/argon2/BizCode/Res<T> 序列化/enforce 決策/redact/SQL-build）走 **test-first 單測**；wiring/形狀對映（handler/middleware/連線/migration/round-trip）因 rust-api bin-only 走 **in-crate `#[ignore]` live-postgres** 或 **C-V acceptance（curl + CDP + psql）**，且在 tasks.md **明示「無單元測試」理由**。011 的 Test 3（觸發真 INSERT 失敗驗 rollback）與 012 的 round_trip_live（真 add_policy→重載→has_policy）是「測真實行為而非 mock」的範例。

3. **error code / 契約事實對齊是 load-bearing 風險點，處理到位** — 008 的 BizCode 12-variant 與 base-web `.env`（SUCCESS/LOGOUT/MODAL_LOGOUT/EXPIRED codes）逐一核對，且驗證 base-web 端確實字串比對（`String(code)==='0000'` + `.includes`）→ code 為 JSON 字串這個不變式被測試鎖死。013 延續：1000 防 user enumeration、3333 統一 token 不可用、refresh 只走 8888/5000（程式上不可能回 3333/9999/9998 防死迴圈）、enforce fail-closed、5003 避開 5000 sentinel。**錯誤碼是 base-web↔rust-api wire 契約的一部分，非自由設計。**

4. **facade 邊界 / soft-delete 不變式以「結構 + build-time lint」保證** — 009 建立三重防護（型別層 trait / facade 唯一管道不 re-export Entity / build-time `entity_access_lint.rs` 依路徑豁免），011/013 持續遵守（audit.rs 不碰 entity::、sys_role 透過 `find_active()` 過濾 soft-deleted）。lint 守門員品質遠超 spec（誠實記錄並修掉舊版 brace-stack false-negative + 9+ 對抗性 regression 測試）。**注意 lint 只掃 `src/` 不掃 `tests/`（刻意取捨）。**

5. **文件回填債反覆出現** — 設計時的刻意偏差未同步回權威文件：011 `data-model.md` 仍寫 `Set(None)`（實作 `None→NotSet`）、012 `action.rs:78` 切片修正未留 Deviation Log、013 AppState 多帶 jwt config（**此條已正確記在 state.rs doc + commit**，是反例正面）。**紀律（CLAUDE.md §7.2）**：刻意偏差/正確性修正應回填 data-model / plan Deviation Log，否則日後讀者重蹈坑（INET 42804）或 rebase 誤「修回」。

6. **無狀態 JWT 的固有取捨需在完整 rollout 前拍板** — 013 的 enforce 用 claims 凍結角色 vs getUserInfo 即時查 DB，撤權要等 token 過期；TTL 內不重查是無狀態 JWT 設計取捨，最小機制證明可接受，但完整 policy 矩陣 + 全路由 enforce rollout 時須明確決策（enforce 是否也即時查 DB）。

## 5. 整體結論

**006-013 整體健康，可信為穩固的 Phase 1→Phase 3 起手基線。** 8/8 Ready、零 Critical、零 Important blocker、零 specGap；每個 feature 都嚴守 scope 邊界（無 over-build）、測試分層符合 §3 紀律、facade/soft-delete 不變式以結構+lint 保證、error code 與 base-web wire 契約逐一核對。多數列出的 issue 是設計觀察、刻意取捨或文件回填債，非功能缺陷。

**最該優先動手的 3 件事：**

1. **把「prod image build」固化為加 crate feature 的 acceptance gate** — 這是反覆咬人（009/010/012）的系統性流程缺口，唯一影響「可交付即可上線」完整性的主題。修 `contracts/verification-commands.md` 範本，要求 prod target build，而非靠下游 deploy commit 救火。

2. **清掉文件回填債 + 補 Deviation Log** — 011 `data-model.md` 的 `Set(None)`→`NotSet`、012 `action.rs:78` 切片修正的 Deviation Log + inline 註解。低成本、高槓桿，避免未來 rebase 誤「修回」bug 或重蹈 INET 42804 坑。

3. **登記 Phase 3 rollout 前的兩個拍板點到 CHECKLIST §2 follow-up** —（a）soft-delete partial-unique 的 `ON CONFLICT ... WHERE deleted_at IS NULL` 陷阱（推廣到其餘 6 entity 前必記 DESIGN §6.5）；（b）enforce 角色來源 claims vs DB 即時查 的撤權即時性取捨（配合完整 enforce rollout 拍板）。
